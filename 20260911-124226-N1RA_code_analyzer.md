## Detailed Requirements Understanding

**Problem/Requirement Statement**: The user wants the reply pipeline to be entirely server-owned: persist his message, generate her answer without any client involvement, and have the answer waiting in `nina_messages` whenever he next renders `/nina`.

**The headline finding of this analysis: this architecture already exists, shipped, on `origin/main`.** The `nina-burst-cancel` set (merge `64c3d4b`) split `sendNinaMessage` into a synchronous persist-and-return half and a background turn that runs inside `after()` on the server's wall clock (`runNinaBackgroundTurn`). The code says so in as many words (`lib/nina/actions.ts:1182`): *"That is the whole of 'the app does not care whether user close the app or not': the wall clock belongs to the server."* Her bubbles are ordinary rows; `app/nina/page.tsx` reads them with `listNinaMessages` on every render, so a reply written while the app was closed is part of the history the next open paints. R1's and R2's core mechanism is therefore NOT work to do — it is the baseline this plan must not regress.

What remains are three **measured gaps** where the shipped system still ties visible behavior to a client being open, plus one dead-turn case where "harus menjawab" still requires a human tap:

- **G1 — reopen during flight sees nothing (violates R2).** The cold load decides "she is thinking" with a heuristic that expires at 90 s (`ninaAwaitingByMessage`, `lib/nina/turnflight.ts:125`): the newest row is his AND younger than `NINA_TURN_STALE_MS`. But a turn — and especially a chained burst — legitimately runs to `NINA_BACKGROUND_BUDGET_MS` = 240 s. A runner who reopens at t ∈ (90 s, 240 s) gets `awaiting: false`, no typing indicator, and **no poll** (`app/nina/page.tsx:291` never reads the `nina_turns` claim — "A HEURISTIC, and knowingly", `app/nina/page.tsx:280`). Her reply then lands while the tab sits open and unpolling, invisible until a manual refresh or the next send.
- **G2 — an open tab gives up at 90 s while the server may honestly run to ~210 s (violates R1's spirit and R2).** The client give-up reuses the server's stale deadline: `NINA_TURN_POLL_GIVE_UP_MS = NINA_TURN_STALE_MS` (`lib/nina/turnflight.ts:32`), asserted as an identity in `lib/nina/turnflight.test.ts`. A burst answered through the chain (up to `NINA_TURN_CHAIN_MAX` = 2 follow-up links) can run 3 × ~50 s ≈ 150–210 s. At 90 s the tab raises the 'no-reply' notice — a lie, the turn is alive — and stops polling; the chained replies land unobserved. (The notice's own copy — *"Your message is saved — send another and she will pick it up"* — was written for a dead turn and is wrong for a live one.)
- **G3 — a dead turn is never answered without a human tap (violates R1) — RESOLVED 2026-09-11 by P1-RI-A039 (phase 2: bounded revive-on-arrival, `lib/nina/turnrevive.ts`).** If the `after()` invocation dies (eviction, deploy, crash, ceiling), `sweepStaleNinaChatTurns` (`lib/nina/chatturn.ts:413`) closes the claim `failed`/`stale` **and deliberately retries nothing** — the module header rules out auto-retry because *"an automatic retry on a render path is a model call the runner did not ask for"*. The only recoveries are his 'resend' tap (`resendNinaMessage`, `lib/nina/actions.ts:1784`) or his next send. "Nina harus menjawabnya" is thus best-effort-with-a-manual-fallback today. The repo already owns the pattern for fixing exactly this class: `reviveNinaImageJobs` (`lib/nina/imagerun.ts:786`) re-fires dead image jobs from the `/nina` render — *"arriving on this page is therefore the pipeline's self-repair"* (`app/nina/page.tsx:248`). Chat turns have no equivalent.

The user's raw input is the specification and it outranks the old module-header decision in G3: they are explicitly asking that a sent message be answered regardless, and that the answer be waiting when they open the chat — which is the render-path recovery the old note declined, now requested by name.

**Success Criteria**:

1. A message sent while the app then closes is still answered server-side (existing baseline; must keep holding).
2. Reopening `/nina` at any point while a turn or chain is genuinely in flight shows the typing indicator and delivers the bubbles when they land, without a refresh (closes G1).
3. An open tab stays honest for the server's full legitimate wall clock — no 'no-reply' while a live claim exists (closes G2).
4. A runner message whose turn died gets answered automatically, with no tap, the next time its session is opened — bounded so the repair can never loop or runaway-spend (closes G3).
5. Every reply lands as ordinary `nina_messages` rows, so history-on-reopen needs no new machinery (baseline; must keep holding).

**Key Considerations**:

- **One database truth, one definition of "unanswered".** `pollNinaReply` already answers `awaiting` as `liveClaim(fresh) || ninaAwaitingByMessage(newest, now)` (`lib/nina/actions.ts:2052`). The cold load should ask the same disjunct instead of the heuristic alone — the fix is to give the page the claim read, not to invent a second definition. `lib/nina/turnflight.test.ts` asserts page/poll agreement and must keep asserting it.
- **The give-up's remaining job is the offline phone.** Its comment (`components/nina/ChatScreen.tsx:1094`) is explicit: by the time the old 90 s give-up fired, the server had already closed the row, so the notice was a fact; the give-up exists for polls that cannot reach the server at all. Raising the backstop to the background budget keeps that job and removes the live-chain lie, because in the dead case the *server's* `awaiting: false` still stops the poll at ~90 s — the claim read is authoritative.
- **Bounded self-repair.** A revive-on-arrival must be capped: one candidate session (the rendered one — the same bound `NINA_IMAGE_REVIVE_BUDGET` = 1 uses), never while a fresh claim exists, and an attempt cap per runner message so a permanently-`unavailable` vendor cannot turn every page render into a model call. The attempt count must come from `nina_turns` itself, walked newest-first over `nina_turns_user_created_idx` — `tests/db.schema.nina.test.ts` pins that table to exactly one index, so a new index (and any migration) is out.
- **Budget pairing.** `after()` runs for the invoking segment's `maxDuration` (`app/nina/page.tsx:146` carries a literal `300`); `NINA_BACKGROUND_BUDGET_MS` = 240 s documents the pairing. A revive scheduled from the page inherits the same budget — do not relocate the turn runner into a segment that does not carry 300.
- **No new exported server actions.** Every export of a `'use server'` module is an untrusted POST endpoint. `runNinaBackgroundTurn` is unexported today, correctly (its input carries a raw `userId`). A revive module must share the turn runner without widening the action surface.
- **Ordering trap between the two fixes**: the page's claim read must happen *after* a revive has had its say (revive sweeps stale claims and may open a fresh one), or the freshly-reopened turn would be computed as "not awaiting" and its answer would land unobserved — G1 re-created by the fix for G3.
- Out of scope, deliberately: push notifications for landed replies (the requirement is visibility-in-history on open, which the render already delivers), the proactive cron (`/api/cron/nina`, and the Hobby plan caps crons at the two already used), the describe pre-pass (runs during composition, client-open by definition), and the resend UI (stays as the manual override).

## Current Dataflow

### Entry Point: `sendNinaMessage` (Server Action)

**Location:** `lib/nina/actions.ts:340`
**Trigger:** `ChatScreen.handleSend` (the only caller)
**Input:** `{ body, imageTickets?, replyToMessageId?, runId?, attachExisting?, dedupedImageIds?, contentHashes?, sessionId }`
**Synchronous half (returns to the client):** validate/refuse → verify tickets → resolve reply target, run, attachments, session → **INSERT the runner's row** (`insertNinaMessages`, :664) → INSERT image rows → sweep stale turns (:924) → supersede a thinking turn (:953) → open the `nina_turns` claim (:965) → return `{ ok, userMessageId, sessionId, cursor, turnId }` (:1003).
**Background half (`startNinaBackgroundTurn`, :1203):** `after(() => runNinaBackgroundTurn(input))` — registered in the action, executed after the response, on the segment's 300 s budget.

### Processing Chain (background turn)

1. **`runNinaBackgroundTurn`** (`lib/nina/actions.ts:1245`) — load context/history/tuning/shortcuts → `runNinaTurn` (13–45 s, `lib/nina/turn.ts`) → ownership re-check (`chatTurnWasSuperseded`) → session-exists re-check → INSERT her bubbles (`turn_id` stamped) → close the claim → distillation → auto-title. Never throws; every failure ends in a closed row with a reason.
2. **The chain** (:1649–1698) — if the newest row in the session is still his and `depth < NINA_TURN_CHAIN_MAX` (2) and wall clock < `NINA_BACKGROUND_BUDGET_MS` − `NINA_TURN_BUDGET.overall`, open the next claim and recurse in-process.
3. **`pollNinaReply`** (`lib/nina/actions.ts:1994`) — the open tab's channel: three indexed reads (rows after cursor, newest row, pending claim), sweep-on-expired, returns `{ awaiting: live(fresh) || heuristic, bubbles, cursor }`.
4. **Cold load** (`app/nina/page.tsx:291`) — `ninaFlightView(rows, now)` = `{ awaiting: newest is his && < 90 s, cursor }`. The claim is never read here; `ChatScreen` starts the arrival loop only on `awaiting`.
5. **Arrival loop** (`components/nina/ChatScreen.tsx:1100`) — sequential backoff poll; stops on server `awaiting: false`; hard give-up at `NINA_TURN_POLL_GIVE_UP_MS` (90 s) → 'no-reply' notice.
6. **Death path** — `sweepStaleNinaChatTurns` (`lib/nina/chatturn.ts:413`) closes `pending` claims older than 90 s as `failed`/`stale`; runs on send and on expired polls only. Nothing retries. `resendNinaMessage` (:1784) is the manual recovery: rebuild the turn input from the row, sweep, open, `startNinaBackgroundTurn`.

### Data Persistence

**Database:** `nina_messages` (both roles, `seq` bigserial, `turn_id`, `reply_to_id`), `nina_turns` (one row per model call; `kind='chat'`, `status`, `error_code`-as-phase, `args jsonb` = `{sessionId, runnerMessageId, depth}`), `nina_message_images`, `nina_memory_*` (distillation), `nina_chat_sessions` (title).
**Cache:** none on this path.

### Exit Points

- Her bubbles as rows → rendered by `app/nina/page.tsx` on any later render (the R2 baseline).
- Poll DTO → staggered reveal in the open tab.
- Log lines + `nina_turns` ledger rows on every failure mode.
