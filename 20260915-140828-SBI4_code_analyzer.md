## Detailed Requirements Understanding

**Problem statement:** Text search over the album (`lib/nina/queries/avatarsearch.ts`) already
shipped a relevance floor and an id+score readout in `751e034` (see Correction 1 below — this
predates this analysis and already lives on `main`), but the operator still hits irrelevant
results and currently has no fast path from "this result is wrong" to "fix its description", no
secondary tagging signal besides free-text `description`, and no repeatable way to diagnose *why*
a specific photo matched a specific query.

**Success criteria:**
- R1: clicking the new button in the open viewer lands the operator on that exact photo's
  description panel, already selected, regardless of which folder the photo lives in or which
  page it would fall on.
- R2: a `search_keywords` value survives save, participates in the embedded text so search can use
  it, survives a re-describe (which only touches `description`), and every pre-existing row's
  embedding is regenerated once through the same combine-then-embed code path.
- R3: `/search-analysis <query> <#id-or-partial-id>` resolves the id, runs the production scoring
  SQL unfiltered (no 48-row cap, no 0.2 floor) to find the target's true rank among every embedded
  row, and reports a human-readable inference — without calling any write path.

**Key considerations / constraints (see Corrections for what changed the plan from the user's own
framing):**
- No relevance-threshold/scoring change is in scope (R3 is diagnostic only).
- `NINA_SEARCH_LIMIT` (48) is a hard **ceiling** inside `clampLimit()` — `searchNinaAvatarsByText`
  structurally cannot return more than 48 rows no matter what a caller asks for, and
  `rankByDistance` applies `NINA_SEARCH_MIN_SCORE` (0.2) unconditionally. Neither R3's script nor
  any future diagnostic tool can see "true rank" by calling the exported search functions; it has
  to run the same SQL those functions run, unfiltered — exactly what `scripts/album-search-probe.mjs`
  already does today for threshold tuning.
- `scripts/` deliberately never imports `lib/nina/embedding.ts` or other `server-only` lib code —
  see that file's own header — so a new diagnostic script must follow the same raw-SQL,
  direct-`fetch`, duplicated-constant pattern, not `embedNinaText`/`searchNinaAvatarsByText`.
- The album is folder-scoped and paginated server-side (`app/admin/nina/page.tsx`): the client only
  ever holds the currently-loaded folder+page's `photos` array, and selection
  (`FileExplorer`'s `selectedId`) is a `photos.find(...)` over that array. A search result photo
  can live in **any** folder, so a "select it" deep link needs the server to resolve which folder
  (and which page within it) the target id is on before the client can select it — this is real,
  previously-nonexistent server work, not a client-only change.

## Corrections to the User's Own Framing (found during exploration, before any phase was planned)

**Correction 1 — the id+score display already shipped, in `751e034` (deployed, and now the base of
this plan set).** Local `main` was one commit *behind* `origin/main` when this analysis started
(fast-forwarded to `751e034` as the first step). That commit already:
- Added `NINA_SEARCH_MIN_SCORE = 0.2` (provisional) to `lib/nina/queries/avatarsearch.ts`, cutting
  rows below the floor from the returned page.
- Added a `meta?: string` field to `PhotoViewer`'s `ViewerPhoto` (`components/ui/PhotoViewer.tsx`),
  rendered in the header next to the name: `#${hit.id} · ${hit.score.toFixed(3)}` (full row id,
  not a truncated form — `components/admin/explorer/SearchResultsGrid.tsx`'s `photos` mapping).
  The tile's `title` attribute also carries `· #${hit.id}`.
- Added `scripts/album-search-probe.mjs`, a read-only Node script that embeds a query via
  OpenRouter directly and re-runs the search's exact SQL (same `<=>` cosine distance, same
  `1 - distance` similarity, same `JSON.stringify` vector encoding) with **no limit and no
  threshold**, printing the full ranked distribution and the largest score gaps.

So the user's `#Rm2NG` in their message is a **truncated paraphrase** of a full 12-character
nanoid id they already see in the deployed UI (the `..` in "saya klik gambar #Rm2NG.." is the
user's own ellipsis) — it is not evidence of a 5-character display-id convention. **R1 therefore
does not need to introduce any id display or format** (already shipped); it only needs to add
navigation from that already-visible id to the description panel. **R3's "part-of-image-id" is
still a useful lookup mode** (an operator typing from memory may only get a suffix right), so the
suffix/substring lookup is kept.

**Correction 2 — cross-folder/cross-page navigation is the real work in R1**, not a display
format. `components/admin/FileExplorer.tsx` holds `photos: readonly ExplorerPhoto[]` — one
server-rendered folder+page — and `selected = photos.find((photo) => photo.id === selectedId) ??
null` (`FileExplorer.tsx:196`). A search result can be in a folder other than the one currently
open (search runs "across every folder", `avatarsearch.ts`'s header), so `?avatar=<id>` cannot be
satisfied by client state alone: the server must resolve `id -> folder` (and which page that id
falls on inside `listNinaAvatarsInFolder`'s ordering, `(created_at desc, id desc)`, per
`nina_avatars_user_folder_created_idx`) before `app/admin/nina/page.tsx` loads the folder/page that
actually contains the row, so the client's `photos` array has it to select.

**Correction 3 — the embedding choke point is narrower than "wherever description is embedded".**
Exactly one function turns prose into a vector: `embedNinaAvatarDescription(description, userId)`
in `lib/admin/ninaAlbumDeferredDescribe.ts:138`, which calls `embedNinaText(description,
{userId})`. It has exactly two call sites:
1. `describeNinaAvatarAction` (`lib/admin/ninaAlbumDescribeActions.ts:78`) — in-band re-describe.
2. `fillOne` (`lib/admin/ninaAlbumDeferredDescribe.ts:186`) — the deferred worker used by
   `scheduleDescribe`/`scheduleDescribeAll`/`scheduleEmbed`/`fillNinaAvatarDescribeTargets` (i.e.
   every describe, re-describe, hand-edit re-embed, and the backfill route all funnel through
   here).

R2's combine-then-embed logic belongs entirely inside `embedNinaAvatarDescription` (add a
`searchKeywords: string | null` parameter, build `description` or `description + "\n\nKeywords: "
+ searchKeywords` before calling `embedNinaText`) plus updating its two call sites to pass the
row's/target's `searchKeywords`. No other file computes an embedding.

## Current Dataflow

### R1 today (post-751e034, pre-this-plan)

1. Operator types a query in `PhotoSearchBar` → `searchNinaAvatarsAction` (`lib/admin/ninaAlbumSearchActions.ts`)
   → embeds the query, calls `searchNinaAvatarsByText`/`ByImageCaption`/`ByTextAndCaption`
   (`lib/nina/queries/avatarsearch.ts`) → `rankByDistance` filters by `NINA_SEARCH_MIN_SCORE` and
   caps at `NINA_SEARCH_LIMIT` → returns `AdminSearchHit[]` (`{ id, score, filename, url, source,
   folder, ... }`, exact shape in `ninaAlbumSearchActions.ts`).
2. `FileExplorer.onSearchResults` stores the hits in `search` state, clears `selectedId`.
3. `SearchResultsGrid` renders one tile per hit; clicking a tile sets `viewerIndex`, opening
   `PhotoViewer` over the full hits array, each mapped to `{ url, kind, label, meta: '#id · score' }`.
4. **Dead end today:** nothing in the viewer lets the operator go from that hit to the album's
   normal browse-and-select flow. Closing the viewer returns to the search-results grid, which has
   no edit affordance for a photo's description at all — the description panel only exists on
   `PhotoGrid`'s tiles via `AlbumSelectionPane`.

### R2 today

1. `AlbumSelectionPane` mounts `PhotoDescription` with the row's `description`.
2. Save → `editNinaAvatarDescriptionAction({id, description})` → validates via
   `avatarDescriptionSchema` → `setNinaAvatarDescriptionAndEmbedding(userId, id, next, null)` (new
   prose, vector nulled in the same statement) → `scheduleEmbed(userId, id)` (`after()`) → that
   deferred call re-reads the row via `listNinaAvatarDescribeTargets`, calls `fillOne` with
   `describe: false`, which calls `embedNinaAvatarDescription(description, userId)` →
   `embedNinaText` → `setNinaAvatarDescriptionAndEmbedding` again, this time with the real vector.
3. Re-describe → `describeNinaAvatarAction(id)` → `describeNinaImages` (vision model) →
   `embedNinaAvatarDescription(description, userId)` (in band) →
   `setNinaAvatarDescriptionAndEmbedding(userId, id, description, embedding)` in one call, no
   `scheduleEmbed` needed (already has the vector).
4. Search reads only `descriptionEmbedding`; `search_keywords` does not exist yet.

### R3 today

No lookup by partial id exists anywhere (`ADMIN_AVATAR_ID_RE` validates a full 12-char id;
`getNinaAvatar` does an exact `eq`). `scripts/album-search-probe.mjs` is the only tool that shows a
full, unfiltered ranked distribution, and it is built for battery-of-queries threshold tuning, not
per-image diagnosis (no id-lookup argument, no single-row detail report, no comparison framing).
