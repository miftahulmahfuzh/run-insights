## Goal

`runs` gains two additive columns, `distance_estimated` and `splits_estimated` (`boolean NOT NULL DEFAULT false`). They are live in the one production database, written by `commitExtractedRun`, left alone by `applyRunCorrections` unless a caller passes them, and read back by every bare `select()` of `runs`. The records catalog drops a flagged run from exactly the keys R4.3 names. `/r/[id]` prints which values were estimated, inside the existing provenance line. The session narrative is told about the estimate, and the facts and hashes of unflagged runs stay byte-identical to base, so no cached insight is invalidated. No product code sets a flag to true yet. Phase 3 does that through `NewRunInput`.

## Interface Contract

**Deletes:** nothing.
**Renames:** nothing.
**Creates:**
- columns `runs.distance_estimated`, `runs.splits_estimated` (`lib/db/schema/runs.ts`, TS keys `distanceEstimated` / `splitsEstimated`)

 * reconstructed from the Workout Details pace chart is ~1% off, and "a ~1% error must not mint a
 * false PB" (the runner's decision). Each key that reads the estimated quantity, directly or through

 */

const measuredSplits = (c: RecordCandidate): boolean => !c.splitsEstimated

/**
 * §2.2.1 — the honesty rule on the saved screen. **Read-only and run-level.**
 *
 * The design brief: *"a saved run must show where its numbers came from... a distinct treatment for
 * a field I corrected by hand."* Per-field provenance belongs to F05's review screen, which is the
 * only place a field is still editable and the only place a per-field mark can be acted on (R-45
 * settled that it is by section there). Here the question is different and simpler: **can I trust
 * this row?** One line answers it:
 *
 *   `⌁ Read from screenshot · reviewed 20 Aug`
 *   `⌁ Read from screenshot · 2 fields corrected · reviewed 20 Aug · edited 22 Aug`
 *   `⌁ Read from screenshot · distance and splits estimated from the pace chart · reviewed 20 Aug`
 *   `⌁ Entered by hand · reviewed 20 Aug`
 *
 * **The estimate clause (R4.2)** sits right after the source because it qualifies the source: the
 * screenshot was read, but these two values were not printed on it — `lib/extract/chart/*`
 * reconstructed them from the Workout Details pace chart. It names WHICH of the two, because they
 * differ (a Summary can print the distance while the split table is missing). Absent when neither
 * was estimated, exactly like the corrections clause at zero.
 *
 * **No colour, ever.** This is provenance, not a warning: a corrected run is a run someone took
 * more care over, and tinting it amber would say the opposite. The glyph plus the words carry the
 * distinction, per dataviz's "never colour alone" — screenshot it in greyscale (§11) and nothing is
 * lost, because there was nothing in the colour to begin with. An estimate is the same: a
 * reconstruction the runner chose to keep, labelled, not an error.
 *
 * `reviewed_at` and `corrected_at` are two different questions (R-8): "has a human ever confirmed
 * this?" and "when did one last change it?". Both are printed when both exist; neither is inferred
 * from the other.
 */
export function ProvenanceMark({
  source,
  reviewedAt,
  correctedAt,
  correctedFieldCount,
  estimated,
}: {
  source: string
  reviewedAt: Date | null
  correctedAt: Date | null
  /** `Object.keys(extractions.corrections ?? {}).length` — F05 writes it, F08 only counts it. */
  correctedFieldCount: number
  /** `runs.distance_estimated` / `runs.splits_estimated` (R4). Required: every caller decides. */
  estimated: { distance: boolean; splits: boolean }
}) {
  const parts: string[] = [source === 'manual' ? 'Entered by hand' : 'Read from screenshot']

  const estimateClause = estimatedFromChart(estimated)
  if (estimateClause) parts.push(estimateClause)
  if (correctedFieldCount > 0) {
    parts.push(`${correctedFieldCount} ${correctedFieldCount === 1 ? 'field' : 'fields'} corrected`)
  }
  if (reviewedAt) parts.push(`reviewed ${formatDayCompact(jakartaDayOf(reviewedAt))}`)
  if (correctedAt) parts.push(`edited ${formatDayCompact(jakartaDayOf(correctedAt))}`)

  return (
    <p className="text-[11px] font-medium text-ink-3">
      <span aria-hidden="true">⌁ </span>
      {parts.join(' · ')}
    </p>
  )
}

/** The R4.2 clause, or null when nothing was estimated. */

  distance,
  splits,
}: {
  distance: boolean
  splits: boolean
}): string | null {
  if (distance && splits) return 'distance and splits estimated from the pace chart'
  if (distance) return 'distance estimated from the pace chart'
  if (splits) return 'splits estimated from the pace chart'
  return null
}

## Principles applied

- Laziness protocol: no new query, accessor or component. The bare `select()`s in `getRunDetail` / `getReviewedRunsWithChildren` carry the columns for free. `applyRunCorrections` gets a doc line and no code, since its `Partial<NewRunInput>` patch already gives the "omitted = unchanged" contract. The mark is one clause in the existing `ProvenanceMark`, not a new chip. Nina's run facts are left alone (Handoffs).
- Make illegal states unrepresentable: `RecordCandidate` / `RecordRunRow` / `SessionRunFacts` flags and the `ProvenanceMark.estimated` prop are **required**, so a new builder or caller cannot forget them and let an estimate compete or go unlabelled silently. The only optional members are `NewRunInput`'s two flags, because "omitted = leave stored value" is a third state a boolean cannot carry. Their docs say so.
- Encode lessons in structure: the R4.3 exclusion is a table test over **all eleven** keys (`EXCLUDED_BY`, which must name every `RECORD_KEYS` member). A twelfth key fails until someone decides whether an estimate may hold it. The unflagged facts hash is pinned to a literal measured on base, so a later "harmless" `estimated: false` default would fail the build instead of silently re-narrating every run.
- Test behavior, not implementation: the records tests assert winners out of `computeRecords` and qualification per key, not the helper predicates. The facts test asserts the hash and the payload, not the spread.
- Prove it works: Proof compares records on a real Postgres between base and this phase over the same seeded history (J2). It checks production's columns and every existing row by effect (J1), and drives the real edit path to recompute records with flags set (J3).
- Sequence into verifiable units: the production migration is the last step, after format, lint, typecheck, tests, guards and `db:check`, and right after a second origin/main tip check. Nothing irreversible happens before the gates can fail.

## Handoffs

- **Phase 3 (R4.1, derivation half):** `lib/review/commit.ts` derives `distanceEstimated` / `splitsEstimated` from `raw_response.details.estimate` versus the validated draft and passes them through `toRunInput` → `NewRunInput`. In edit mode phase 3 passes both flags explicitly, derived from the stored run (kept estimated distance ⇒ `true`, changed ⇒ `false`; all splits removed ⇒ `false`; an unflagged run ⇒ `false`, a no-op write); an explicit value is written, an omitted one leaves the column as stored. J3 shows an edit that omits the flags keeps them (once phase 3 lands, the same unchanged edit passes them explicitly as `true`, with the same result). The end-to-end journey that commits a real Workout Details upload and finds the flags true plus the mark on `/r/[id]` belongs to phase 3. Phase 2 proves persistence and display only.
- **Phase 3 (docs):** `docs/architecture.md` §4.3 (the migration chain: add `0038`, additive, applied in production during phase 2), §5's `/r/[id]` line and §6 (records: the R4.3 exclusion; insights: `session.estimated`), `CLAUDE.md`'s pipeline paragraph, `features/review-commit.md` / `features/upload-extract.md`. Phase 2 edits only `features/run-detail.md`. (Reconciled: phase 3's Step 10 now carries the §4.3, §5 `/r/[id]` and §6 edits verbatim.)
- **Coordinator, migration collision:** phase 2 applies `drizzle/0038_*` to production during the phase. Keep this file byte-identical and resolve the numbering by hand with the ledger in view (memory: "Migration collisions: regenerate, never rename" assumes the migration was not yet applied, which is not the case here).

## Rollback

Revert this phase's commit(s). The two columns are additive with defaults, so they stay in production unused and harmless (inserts from reverted code omit them and get `false`). Dropping them is a separate migration that must be applied **after** the reverted code is deployed (memory: "A DROP COLUMN applies AFTER the deploy"), because the deployed code's bare `select()` names them until then. No data is lost by a code revert, since nothing sets a flag to true before phase 3.
