## Goal

After this phase, both grids on `/nina/about` — the profile album and the Media tab — are walked by
a row of page numbers with the active page marked, so page 3 is one tap from page 1 instead of two.
The two chevron `Button`s and the two Lucide glyphs that drew them are gone from the file, and the
`Halaman {page} dari {pageCount} · {total} foto` count line under each grid is kept exactly as it
is. Nothing about how the page is fetched changes: it is still `goToAlbumPage` / `goToMediaPage`, a
client Server-Action call against the per-tab cache, with no navigation.

**Renames:** none.

**Creates:** no new exported symbol. `NinaAboutPager` is module-private and keeps its name.

**Signature changes:**

  `NinaAboutPager({ page, pageCount, total, label, busy, onPage })`. Module-private; both call
  sites are in the same file and are updated in Step 2. The new `label: string` exists because the
  shared `Pagination` requires a `label` and the plan's invariant says every mount names the
  collection it walks.

**Kept deliberately — the outer `pageCount <= 1` guard (reconciled 2026-10-01):**

`NinaAboutPager` keeps `if (pageCount <= 1) return null` at the top of its body. This is **not**
redundant with `Pagination`'s own null-at-one-page, and it is **not** an oversight:

- `Pagination` returning `null` withholds only the numbered row. The guard here also withholds the
  `Halaman {page} dari {pageCount} · {total} foto` **count line**, which lives in this function and
  nowhere else.
- `components/nina/NinaAboutScreen.test.tsx:218` (`'a single-page collection shows no Previous/Next
  row'`) asserts `expect(screen.queryByText(/Halaman/)).not.toBeInTheDocument()` — measured on
  `b32d662`. Dropping the guard would start rendering `Halaman 1 dari 1 · 2 foto` under every small
  album: a visible behaviour change nothing in the user's ask calls for, on the screen whose own
  docblock calls the single-page case the common one.

Phase 1's handoff list originally told this phase **not** to add its own guard. **That line was
wrong and the reconciler struck it from `phase-1.md`.** Phase 1 was reasoning from
`components/ui/Pagination.tsx`, where the count line is invisible. Do not re-litigate this at
implementation time; the index records it as `## Decisions` fork 8.

This decision is **per surface, and does not generalise.** Phases 3, 4 and 5 must NOT add an outer
guard: their count lines (`{first}–{last} of {total}`, `Showing … of … · page … of …`) render today
at `pageCount === 1` — verified in the worktree, and
`components/admin/PhotoReferencePicker.test.tsx:191-196` pins `page 1 of 1` as *shown*. Adding a
guard there would be the same unasked-for behaviour change in reverse.

**Requires (from earlier phases):**
- Phase 1: `components/ui/Pagination.tsx` exports
  `Pagination(props: PaginationProps): React.JSX.Element | null`, where the `onPage` arm of the
  union is `{ page, pageCount, label, busy?, className?, onPage: (page: number) => void }`.
- Phase 1: `Pagination` renders `<nav aria-label={label}>` > `<ul>` > one `<li>` per page; the
  active page is a non-interactive `<span aria-current="page">`; every inactive page is a
  `<button type="button" disabled={busy}>` whose only text is the number; it returns `null` when
  `pageCount <= 1`.
- Phase 1: `Pagination` carries no `'use client'` directive, so importing it from this
  `'use client'` file compiles it into the client graph.

**Leaves alone (owned by others):**

- `components/admin/explorer/PhotoGrid.tsx` + test (Phase 3).
- `components/admin/PhotoReferencePicker.tsx` + test (Phase 4).
- `components/admin/PhotoshopPickerGrid.tsx`, `app/admin/error-logs/page.tsx` (Phase 5).
- **Not touched by anyone this phase:** `lib/nina/aboutPageActions.ts`, `lib/nina/album.ts`

### Step 3: Replace the pager's body with the numbered row

```tsx
/**
 * The numbered page row under each grid — one page of `NINA_ABOUT_PAGE_SIZE`, so every photograph
 * in the collection is reachable rather than only the render-capped newest batch. Renders nothing
 * for a single-page collection, the common case: most albums and most conversations do not yet
 * hold 30 photographs.
 *
 * `onPage` is `goToAlbumPage`/`goToMediaPage` — a client fetch, never a navigation (the runner's
 * own choice over a `?page=` link): the page shell never remounts and `busy` is this tap's own
 * flight, not the attach strip's. Those two callbacks already took an arbitrary page number, so
 * a jump to page 5 is one call with `5` and neither of them needed a line changed for this.
 *
 * ── EVERY NUMBER, THEN THE COUNT LINE ────────────────────────────────────────────────────────
 * The two chevron `Button`s are gone. A `Sebelumnya`/`Berikutnya` pair makes page 5 four taps from
 * page 1, and the runner's ask was a row of numbers precisely so that it is one:
 * *"i can jump directly to specific page whenever i want"*. `components/ui/Pagination.tsx` is that
 * row — the one implementation, shared with the four admin surfaces — and it marks the active page
 * itself, so the line below is no longer the only thing saying where you are. The line stays
 * anyway, for the half a row of numbers cannot express: how many photographs there are.
 *
 * The `pageCount <= 1` guard is kept even though `Pagination` already returns `null` in that case.
 * It is not redundant here: it is what also keeps the count line off a single-page collection,
 * which is what this screen has always done and what its test pins.
 */
function NinaAboutPager({
  page,
  pageCount,
  total,
  label,
  busy,
  onPage,
}: {
  page: number
  pageCount: number
  total: number
  label: string
  busy: boolean
  onPage: (page: number) => void
}) {
  if (pageCount <= 1) return null
  return (
    <div className="mt-2 flex flex-col items-center gap-2">
      <Pagination page={page} pageCount={pageCount} label={label} busy={busy} onPage={onPage} />
      <p className="text-[11px] font-medium text-ink-3 tabular-nums">
        Halaman {page} dari {pageCount} &middot; {total} foto
      </p>
    </div>
  )
}
```

**Impact:** `ChevronLeftIcon` and `ChevronRightIcon` now have zero callers (Step 5 removes them).
`Button` keeps four callers in the attach strip, so its import is untouched. The grid above is
unaffected: `NinaPhotoGrid` is rendered by the caller, not by this function.
