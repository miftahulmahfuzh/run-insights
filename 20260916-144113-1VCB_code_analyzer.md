## Detailed Requirements Understanding

**Problem/Requirement Statement:** Nina currently opens a conversation on her own initiative for
exactly five reasons (`lib/nina/proactive.ts`'s `ProactiveTriggerKind`): a run just got recorded,
a pattern got crossed enough times, today is a usual running day with no run yet, he has gone
quiet, or her avatar changed. None of these is "the runner asked to be reminded of something at a
time he named." That is a sixth, structurally different trigger: it is not inferred from his
running data, it is an explicit standing instruction he gave her in a chat turn, with a
runner-chosen daily time and a runner-chosen reason.

**Success criteria:**
1. A chat message shaped like the one quoted above — natural Indonesian prose ending in a
   time-anchored "remind me" request — causes the model to populate a new structured field on its
   `send` tool call (parallel to the existing `memoryWrites` field), which the server validates and
   persists as a standing reminder.
2. Nina's reply in the same turn confirms the reminder in her own voice (no separate
   confirmation mechanism is needed — she says so in the `bubbles` she was already sending).
3. Every day from then on, at 8:45 PM Jakarta time (within the tolerance the app's single cron
   already has to work with — see below), a **new chat message from Nina** and **a push
   notification** land, reminding him to sleep and referencing why (sleep consistency /
   regeneration / liver, as he told her), without a duplicate on the same calendar day and without
   silently going stale.
4. The mechanism must fit inside the app's existing infrastructure with **no new Vercel cron job**
   and **no plan upgrade** — see the Hobby-plan constraint below, which is load-bearing.

**Message-length verification (the mid-turn question), answered:** `lib/nina/schema.ts:44` defines
`MAX_RUNNER_MESSAGE_CHARS = 4000`, enforced at `lib/nina/actions/send.ts:426`
(`if (text.length > MAX_RUNNER_MESSAGE_CHARS) return REFUSED`) — an over-cap message is refused
outright and never silently truncated (confirmed by the surrounding comment: *"an oversized-paste
refusal is unchanged... the oversized one is a paste of a whole article — neither is worth a
persisted row"*). The composer's `<textarea>` (`components/nina/Composer.tsx`) carries no
client-side `maxLength` either. The user's actual pasted bubble measures **3,347 characters** —
under the 4,000 cap — so it would be sent to Nina whole, with no truncation and no refusal. This is
not a bug; no fix is needed. There is a separate cap, `MAX_BUBBLE_CHARS = 700`
(`lib/nina/schema.ts:29`), but that bounds **Nina's own outgoing reply bubbles**, not what the
runner may send in.

**Key considerations / constraints discovered:**

- **Vercel Hobby plan, and it is the load-bearing constraint of this whole feature.**
  `docs/architecture.md:26` and multiple files confirm the project is on Vercel Hobby. Hobby caps
  an account at **two** cron jobs total (already fully used: `/api/cron/rollup` and
  `/api/cron/nina`, per `app/api/cron/nina/route.ts:25-27`) and each cron fires **at most once a
  day**, landing "within the hour" of its declared UTC time rather than at the exact minute. A
  third, minute-resolution cron for arbitrary per-reminder times is **not available** on this
  plan, and adding one is out of scope for this feature (it would require a plan upgrade, which is
  a decision for the user to make separately, not one this plan makes for him).
- `.github/workflows/nina-image.yml`'s own header **measures** its `schedule:` cron as unreliable
  for anything time-sensitive (gaps of 1h46m–4h19m against a declared `*/10m`, and GitHub
  deprioritizes `schedule:` on low-activity repos). This rules out a GitHub Actions cron as a
  precise, dependable way to hit an exact reminder time.
- The existing `/api/cron/nina` route already runs **once a day**, currently scheduled
  `"0 12 * * *"` (19:00 WIB — see the route's own header derivation), with a firing window Vercel
  Hobby describes as "within the hour" (so, empirically, sometime in 19:00–20:00 WIB). The
  requested reminder time, 20:45 WIB, falls **after** that window, so the schedule must move later
  to ever reach it same-day.
- The four existing evening triggers already tolerate a moving cron time: `MISSED_DAY_EVENING_HOUR
  = 18` and `MISSED_DAY_LATEST_HOUR = 23` (`lib/nina/proactive.ts:95-96`) is a wide **admission
  window**, not an exact hour — moving the cron's actual fire time later inside that window changes
  nothing about when those four are allowed to fire.
- There is **no existing per-minute Jakarta wall-clock helper.** `lib/date/ranges.ts` and
  `lib/nina/proactive.ts` only go down to the **hour** (`jakartaHourOf`) or the **calendar day**
  (`todayInJakarta`, `DateISO`). A reminder needs an `HH:mm` comparison, which nothing in this
  codebase currently computes.
- There is **no existing "reminder" or "alarm" concept anywhere in the repo** (grepped `lib/`,
  `app/`, `components/` for `reminder|alarm`, case-insensitive — the only hits are unrelated uses
  of the English word "alarming"). This is new ground, not an extension of something partially
  built.
- The closest existing analogs, and what each contributes:
  - **`lib/nina/promises.ts` + `lib/nina/promise.ts`** — "something becomes due on a schedule, is
    evaluated idempotently on every cron tick, and fires an action" is exactly this shape.
    `resolveNinaPromises` reads a `jsonb` memory-slot list (`pending_promises`), evaluates each
    entry against today's facts, and is safe to call every tick because nothing is fired twice for
    the same day. `nina_memory_slots` already stores **list-shaped, schedule-tracked data with no
    migration**, via the `jsonb` column — this is the template for storing reminders too, rather
    than a new table.
  - **`lib/nina/proactive.ts` + `lib/nina/nags.ts`** — the five-trigger evening engine, its
    "at most one proactive message per tick" resolver (`decideProactive`/`PROACTIVE_PRIORITY`), its
    marker-after-persist ordering (write the message, THEN the durable marker, never the reverse —
    a failure before the marker is retried by the next tick instead of being silently lost), and
    its notify-last, best-effort push step. A sixth trigger (`reminder_due`) slots into this exact
    machine.
  - **`SEND_TOOL.memoryWrites`** (`lib/nina/prompts/tools.ts:97-123`, validated by
    `NinaMemoryWriteSchema` in `lib/nina/schema.ts:46-56`) — the precedent for "a side-effect field
    riding along on the same `send` tool call that produces her reply," which avoids an extra
    model round trip. A reminder request is exactly this shape: something revealed in the turn,
    persisted alongside the reply, with no need to block the reply on it.

**Edge cases this phase must decide, decided below (see the plan's `## Decisions`):**
- What happens when a pattern-nag and a due reminder compete on the same tick (priority order).
- What the model is shown so it can *cancel* a reminder later ("gausah reminder lagi") — it needs
  the existing reminder's id in its context, the same way `pending_promises` already is.
- Whether reminders live in a new table or the existing `jsonb` slot mechanism.
- How "is it due" is computed given the cron only fires once a day at a moving, imprecise time.

## Current Dataflow

### Entry point: the runner's chat message

**Location:** `components/nina/Composer.tsx` → a server action in `lib/nina/actions/send.ts`.
**Trigger:** the runner submits the composer.
**Validation:** `lib/nina/actions/send.ts:417-428` — empty-and-nothing-else refused; over
`MAX_RUNNER_MESSAGE_CHARS` (4000) refused; too many photo tickets refused. The user's message (3,347
chars) passes both checks untouched.
**Next step:** the message is persisted, and `lib/nina/turn.ts`'s `runNinaTurnWith` is invoked with
the full context (`lib/nina/context.ts`), running the model loop described below.

### Processing chain: one model turn

1. **`runNinaTurnWith`** (`lib/nina/turn.ts:838-1058`) sends the system prompt
   (`buildNinaSystemPrompt`) plus the conversation to the model with the core tool set
   (`SEND_TOOL`, `LOOKUP_RUNS_TOOL`, `COMPARE_RUNS_TOOL`, `AGGREGATE_RUNS_TOOL`,
   `SAVE_MEMORY_TOOL`), forcing `send` on the last allowed round.
2. Today, given the user's message, the model has no tool through which to express "remind him at
   8:45 PM daily" other than prose inside a `bubbles` entry — there is nothing that persists it.
   That is the gap this feature closes: a `reminders` field on `SEND_TOOL`'s payload, validated by
   a new Zod schema, alongside the `bubbles` that confirm it.
3. **`runNinaTurnWith`** returns `NinaSendPayload` (currently `{ bubbles, replyToMessageId?,
   memoryWrites? }`) to **`turnrun.ts`**, which persists the bubbles, notifies via push
   (`'chat_reply'`), and hands `memoryWrites` to `runNinaDistillation`.

### Processing chain: the evening cron (where the reminder later fires)

1. **`GET /api/cron/nina`** (`app/api/cron/nina/route.ts:86-180`), once daily, `CRON_SECRET`-gated,
   iterates active users.
2. Per user: `resolveNinaPromises(userId)` sweeps promises, then `evaluateAndEmitForUser(userId)`
   (`lib/nina/proactive.ts:791-824`) loads `NinaContext` + `ProactiveFacts`
   (`loadProactiveFacts`, `:532-567`) and calls the pure `decideProactive` (`:376-395`), which
   returns at most one `ProactiveDecision` across the five triggers, by `PROACTIVE_PRIORITY`.
3. If a decision fires, `emitProactiveMessage` (`:593-718`) builds the trigger-specific prompt
   appendix (`buildProactiveInstruction` + `triggerBlock`), runs a fresh model turn with
   `proactive:` framing, persists the resulting bubbles with `source = detail.kind`, writes the
   durable marker (`markerFor`, only after the message rows exist), and notifies via
   `pushNotifier` — which requires `kind` to be a value `NINA_PUSH_KINDS` also lists.

### Data Persistence

- **`nina_memory_slots`** (`userId`, `key`, `value: jsonb`) — where `pending_promises` already
  lives as a JSON list with no dedicated table; this phase's `reminders` slot is a sibling key, no
  migration.
- **`nina_nags`** (`userId`, `code`) — the pattern-nag/missed-day/silence markers; **not** where a
  reminder's "already fired today" marker belongs, because that marker has to live beside the
  reminder's own `timeOfDay`/`label`/`message`, which `nina_nags` has no columns for.
- **`nina_messages`** — every proactive message, including a future `reminder_due` one, is a normal
  row with `source = 'reminder_due'`, exactly like the other five.
- **Push subscriptions** — unchanged; `sendNinaPush` fans out to whatever is live for the user.

### Exit Points

- A confirmed reminder: the model's own `bubbles` in the same turn (no new UI, no new endpoint).
- A daily check-in: a `nina_messages` row plus a Web Push notification, exactly like the other four
  proactive triggers — same tap-through behavior, same TTL, same failure handling.

## Key Data Structures

### `NinaSendPayload` (`lib/nina/schema.ts:68-78`)
Currently `{ bubbles: string[]; replyToMessageId?: string; memoryWrites?: NinaMemoryWrite[] }`.
Gains an optional `reminders?: NinaReminderWrite[]`.

### `NinaMemoryWrite` (`lib/nina/schema.ts:46-56`)
`{ kind: 'slot' | 'fact'; slotKey?: string; text: string }` — the shape a new
`NinaReminderWriteSchema` (`{ action: 'create' | 'cancel'; id?; timeOfDay?; label?; message? }`)
sits beside, not inside — a reminder is not a slot/fact string.

### `NinaPendingPromisesSlot` / `NinaPendingPromise` (`lib/db/schema/nina/memory.ts:46-112`)
The direct structural template for a new `NinaRemindersSlot` / `NinaReminder` pair — a `jsonb`
list, each entry carrying its own status and date-tracking fields, parsed tolerantly
(`lib/nina/promises.ts:182-189`'s `parseSlot` pattern) rather than trusted raw off the column.

### `ProactiveFacts` / `ProactiveDetail` / `ProactiveDecision` (`lib/nina/proactive.ts:133-200`)
The exact shape a sixth trigger's facts and detail variant extend — `reminders` and `nowHHmm`
join `ProactiveFacts`; a `ReminderDueDetail` joins the `ProactiveDetail` union.

1. `lib/nina/schema.ts` — new `NinaReminderWriteSchema`, `reminders` field on
   `NinaSendPayloadSchema`.
2. `lib/nina/prompts/tools.ts` — `reminders` property on `SEND_TOOL.input_schema`; bump
   `NINA_PROMPT_VERSION`.
3. `lib/nina/reminders.ts` (new) — pure module: `NinaReminder` type, `NINA_SLOT_REMINDERS` key,
   `parseRemindersSlot`, `applyReminderWrites`, `markReminderFired`, `evaluateReminderDue`,
   `jakartaMinuteClockOf` (or sited in `lib/nina/proactive.ts`/`lib/date/ranges.ts` — planner's
   call, stated as an open implementation decision, not a fork needing user input).
4. `lib/nina/prompts/system.ts` — `ProactiveTriggerKind` gains `'reminder_due'`; a
   `PROACTIVE_COPY`/`PROACTIVE_INSTRUCTIONS` entry for it; a short teaching note on when/how the
   model should populate `SEND_TOOL.reminders`.
5. `lib/nina/proactive.ts` — `PROACTIVE_PRIORITY` gains `reminder_due` (front, per Decisions);
   `ProactiveFacts`/`ProactiveDetail` extended; `loadProactiveFacts` reads the reminders slot;
   `decideProactive`'s evaluator map gains the sixth entry; `markerFor`/`emitProactiveMessage`'s
   marker-write step special-cases `reminder_due` to write back into the reminders slot instead of
   `nina_nags`; `triggerBlock` gains a case.
6. `lib/nina/turnrun.ts` — after persisting bubbles, apply `result.payload.reminders` via the new
   applier (own `try`/`catch`, logged, never throws — matching the file's existing resilience
   idiom), independent of `runNinaDistillation`.
7. `lib/nina/context.ts` (verify + likely touch) — active reminders need to be visible to the model
   in context (the same way `pending_promises` already is) so it can reference an existing
   reminder's `id` to cancel it, and so it does not create a duplicate for a request it already
   fulfilled.
8. `lib/push/payload.ts` — `'reminder_due'` added to `NINA_PUSH_KINDS`; whatever title/body mapping
   `buildNinaPushPayload` keys off `kind` gets a case (planner to confirm exact shape of that
   mapping — not fully read in this analysis pass).
9. `vercel.json` — `/api/cron/nina`'s schedule moves from `"0 12 * * *"` to a time that brackets
   20:45 WIB inside Hobby's "within the hour" tolerance (Decisions below name the exact value).
10. `app/api/cron/nina/route.ts` — header comment block updated to match the new schedule's
    UTC/WIB arithmetic (currently documents `"0 12 * * *"` / 19:00 WIB by name).
11. Tests: a new `tests/nina.reminders.test.ts` (pure-function, no DB/model, mirroring
    `tests/nina.nags.test.ts`); extensions to `tests/nina.proactive.test.ts` (priority ordering
    including the sixth trigger) and to wherever `NinaSendPayloadSchema` /
    `ProactiveTriggerKind`/`NINA_PUSH_KINDS` parity is already asserted
    (`tests/nina.prompts.test.ts` or equivalent — planner to locate exactly).
