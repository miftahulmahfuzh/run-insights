## Goal

The string `revision` no longer exists anywhere in the image-prefs stack: not as a drizzle column
(dropped by a generated migration), not as a member of `NinaImagePrefs` /
`NinaImagePrefsWrite` / `NinaImagePrefsInput` / `AdminImageGenResult` / `ImageGenPanelProps`, not
as a computed `+1` in the upsert, and not as "Revision N" copy on the page, the panel, or the
`/admin` hub card. The row is one configuration record upserted in place — configuration tuning,
not a prompt history. `updatedAt` stays: it records row freshness, not versioning.

### Step 15: DEPLOY RUNBOOK — part of this phase, executed in this order at landing time

This repo's single database IS production (`DATABASE_URL` in `.env.local` is the instance
production reads — there is no separate dev instance, and `db:migrate` writes production). The
ordering is a correctness constraint, not a preference:

1. **Land the CODE first** — merge/deploy the phase's commit. Do not run `db:migrate` from the
   worktree before the deploy.
2. **Between deploy and migrate, the system is safe by construction.** The deployed schema
   declares no `revision` column while the table still has one. The read path is a bare
   `select().from(ninaImagePrefs)` (`readNinaImagePrefs`), and drizzle expands a bare select to
   the SCHEMA's column list, so the table's extra column is simply not read — ignored, not an
   error. The write path no longer names the column anywhere (step 2 removed the INSERT value and
   the `set` clause), so an extra stored column is equally inert. Every read and every save works
   in this window.
3. **Then run `npm run db:migrate`.** Verify against the database, not the exit code (memory:
   a green exit is not the question answered): the row for tag
   `0017_retire_imageprefs_revision` exists in `drizzle.__drizzle_migrations`, and
   `SELECT column_name FROM information_schema.columns WHERE table_name = 'nina_image_prefs'`
   lists fifteen columns with no `revision`.
4. **The reverse order breaks every write.** Old deployed code INSERTs `revision: 1` by name and
   computes `revision + 1` inside its upsert's `set`; against a dropped column, every save and
   every reset fails for as long as that code is live. Migrating first is the one unrecoverable
   mistake in this phase — the code deploy cannot be un-shipped as cheaply as a migration can be
   postponed.
5. **Rollback after migrate:** revert the code, then restore the column with
   `ALTER TABLE "nina_image_prefs" ADD COLUMN "revision" integer NOT NULL DEFAULT 1;` —
   historical counter values are unrecoverable, and the counter had no consumer, so reconstructed
   values are harmless. If the migration has NOT run yet, reverting the code alone is complete and
   the database was never touched.
