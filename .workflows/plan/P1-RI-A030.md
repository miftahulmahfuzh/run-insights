## What the card asks for

A dry-run-by-default, **read-only** audit script over `nina_message_images` reporting, per user:

1. reference rows (`source_avatar_id` or `source_image_id` non-null)
2. rows sharing a `pathname` with another row
3. orphans (`message_id IS NULL`)
4. rows whose `source_image_id` points at a row that no longer exists

Plus: is the collection genuinely empty, or are the reads filtering everything out — raw table
count alongside what the collection-defining query functions actually return. Deletes nothing,
writes nothing.

**Resolution:** the audit computes three counts side by side instead of the two the card names —
raw table count, `generatedChatPhotoScope`'s count (kind='generated' AND isOriginalPhoto AND not
already adopted into the album), and the count `countNinaMediaPhotos`/`listNinaMediaPhotos`
actually return today (`isOriginalPhoto()` alone, no `kind` arm) — and the report says outright
that `listNinaMessageImages` no longer exists and names its replacement. This is the narrowest
reading that still answers the card's real question ("is the collection empty for real, or is a
read over-filtering") using the query surface as it exists today rather than as it existed when
the card was filed.

## Ambiguity call (narrowest reading)

The card says *"It must delete nothing and write nothing without an explicit `--apply`."* Every
sibling script in `scripts/nina-dedupe-*.mjs` and `scripts/blob-reap.mjs` carries exactly that
sentence, gating a real write path. This card's own first line is *"Read-only audit; deletes
nothing,"* its "What to build" list names four *report* items and one *diagnostic* question, and
its Notes section says explicitly *"this card does not do"* the recovery work. There is no
mutation named anywhere in the card for a hypothetical `--apply` to gate.

**Narrow reading (built):** the script is unconditionally read-only — no `--apply` flag exists at
all, because there is nothing for it to unlock. The boilerplate sentence is read as inherited
phrasing from the family of scripts this one sits beside, not as a requirement to invent a write
path with no defined target.

**Wide reading (rejected):** implement an `--apply` flag now, for some future write the card never
names. Rejected under 4c — inventing the shape of a mutation the card does not specify is scope
the card explicitly disclaims, and a flag with no effect (or an effect I made up) is worse than no
flag: `npm run lint`/`knip` would flag dead branches, and a future reader would have to reverse-
engineer what "apply" was ever supposed to do.

## Design

**File:** `scripts/nina-chat-photo-audit.mjs`

Exported pure functions (tested without a database, `tests/nina.chatPhotoAudit.test.ts`):

- `isOriginalPhotoRow(row)` — mirrors `isOriginalPhoto()`: `sourceAvatarId == null &&
  sourceImageId == null`.
- `chatPhotoAdoptedIds(avatarRows)` — mirrors the `notExists(... source_key = 'chat-photo:' ||
  id ...)` arm: builds the `Set` of `nina_message_images.id`s already copied into the album, from
  `nina_avatars.source_key` values prefixed `chat-photo:`.
- `matchesGeneratedChatPhotoScope(row, adoptedIds)` — mirrors `generatedChatPhotoScope`: `kind ===
  'generated' && isOriginalPhotoRow(row) && !adoptedIds.has(row.id)`.
- `matchesMediaCollectionScope(row)` — mirrors the unexported `mediaCollectionScope`:
  `isOriginalPhotoRow(row)` (no `kind` arm).
- `auditChatPhotoRows(rows)` — the four report categories: `referenceRows`, `orphanRows`,
  `danglingSourceImageRows` (a `source_image_id` naming an id absent from the loaded set),
  `pathnameDuplicateGroups` (rows grouped by `pathname`, groups of size > 1 only).

`main()` (behind `if (import.meta.url === pathToFileURL(process.argv[1]).href)`, the
`nina-profpic.mjs` guard this repo already uses):

1. Preflight: require `DATABASE_URL`, exit 2 with a clear message if absent (`nina-dedupe-media.mjs`'s
   convention).
2. `neon(process.env.DATABASE_URL)`; load every row of `nina_message_images` (id, user_id,
   message_id, kind, source_avatar_id, source_image_id, pathname, created_at) and every
   `nina_avatars` row's `(user_id, source_key)` where `source_key` starts with `chat-photo:`.
   **Does not refuse on 0 rows** — unlike `nina-dedupe-media.mjs`, an empty table is this script's
   most likely and most important finding, not a wrong-database signal.
3. Compute, globally and per `user_id`: raw count, `generatedChatPhotoScope` count,
   `mediaCollectionScope`-equivalent count, and the four `auditChatPhotoRows` categories.
4. Print a report to stdout: the three-way count comparison with an explicit verdict sentence
   (genuinely empty vs. over-filtered vs. normal), then each of the four categories, grouped by
   user, naming row ids, pathnames and timestamps so a human can decide whether the recovery
   follow-up card is worth opening.
5. Exit 0 always on a successful read (this is a report, not a check with a pass/fail state); exit
   2 only on a connection/config failure.

No `--apply`, no `del()`, no `@vercel/blob` import, no `UPDATE`/`DELETE`/`INSERT` anywhere in the
file.

**`package.json`**: one new line beside the other `nina:` entries —
`"nina:chat-photo-audit": "node --env-file=.env.local scripts/nina-chat-photo-audit.mjs"`.

No migration, no schema change, no `lib/**` edit — every column this script reads already exists
and is already applied to production (the card's own "Notes": migration `0013` verified against
the database).
