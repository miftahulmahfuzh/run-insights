## Why

The user's rationale, verbatim. This is the specification.

> there is a serious bug right now, in that we chat photos, where photos collection that were painstakingly generated by llm, will be deleted if user delete chat session.. keep each photo unique accross Chat Session and Nina Album.. but don't delete existing photos, if user delete a chat session, just let the photos be.
> another problem is that i have replaced some photos in Chat photos , but when i delete chat sessions, these photos (that i replaced manually) got deleted as well.
> i think the change that i want to implement is that we must allow "orphaned" photos in Chat photos collection. we just need to make sure there are no photos from Nina's album that got carried over to Chat photos, and there are no duplicated photos in Chat photos as well

And, in a second message:

> make sure these "orphaned" photos got "parent" chat session again if user attach a photo to another chat session

**Read together, those four sentences change what a chat photograph IS.** It stops being a child of
a bubble — the shape `nina_message_images.message_id NOT NULL ON DELETE CASCADE` encodes and the
column's own comment defends (*"an image with no message is nothing"*) — and becomes a durable
object with an OPTIONAL parent. The photographs outlive the conversations they appeared in, and a
conversation is one place a photograph can be shown rather than the reason it exists. Every decision
below follows from that one reversal, and the column comment that states the opposite is rewritten
by phase 1 rather than merely contradicted by it.

## Scope

**In scope**

- `nina_message_images.message_id` becomes nullable with `ON DELETE SET NULL`, so a session delete
  (and its message cascade) leaves the photograph rows standing.
- `nina_message_images.is_reference` — one boolean that says "this row re-shows a photograph that
  already exists elsewhere; it is not itself a member of the collection". The Chat photos collection
  predicate gains it, and the album-share path is its only new writer.
- `resolveAttachment` and the attached-photo insert in `sendNinaMessage` become **adopt-or-reference**:
  an `image` pointer at an orphaned row of his adopts that row onto the new message; anything else
  writes a reference row.
- `deleteNinaMessage` keeps taking its own photographs, explicitly rather than by cascade.
- Every reader that assumed a photograph has a message: `imageColumns`/`NinaImageRow`, `ImageLike`,
  `NinaGalleryPhoto`/`galleryPhotos`, `app/nina/page.tsx`'s photo `Map`, the `/admin/photos` DTO and
  its detail rail, and `removeChatPhotoAction`'s carrier lookup.
- **The session-delete confirmation copy**, which currently promises the photographs go with the
  chat. Added at reconciliation; see Decisions, row 8.
- A dry-run-by-default backfill that brings existing violating rows into line.

**Out of scope**

- **Deleting anything.** No phase deletes a row, and no phase deletes a Blob object.
  *"don't delete existing photos"* is the overriding value in this request, and it constrains the fix
  as much as the behaviour.
- Removing the album→chat share (F34 R2) or the re-attach loop (F33 R26). Neither was mentioned;
  both keep working. See Decisions.
- A unique index on `(user_id, pathname)`. See Decisions.
- The memory-ledger purge in `removeNinaSession` (R8 of the sessions set) — statements 1–3 are
  untouched. A deleted conversation still stops teaching Nina; only its photographs survive it.
- `nina_avatars`, `/admin/nina`, the album's folders and thumbnails.
- Blob reaping. `scripts/blob-reap.mjs` is unchanged, and **must not be run against `nina/` until
  phase 3 has been applied** — the bytes of every photograph already lost to this bug are still in
  the store, unreferenced, and a reap would make R1 retroactively unrecoverable.

## Invariants

1. **The tree builds and the suite passes at the end of every phase.** `npm run typecheck`,
   `npm run lint`, `npm test`.
2. **Nothing is deleted to satisfy this plan.** No new `DELETE` and no new `del()` reaches a row or
   an object that a human did not explicitly ask to remove.
3. **One migration, and phase 1 owns it.** No other phase runs `npm run db:generate`. A second
   generated migration in a parallel phase collides in `drizzle/meta/_journal.json`, and a renamed
   migration is skipped silently.
4. **Owner scope on every new statement** — `user_id` in the WHERE, including the adoption UPDATE.
   A photograph id from a client is a claim.
5. **No unconditional `del()` becomes reachable.** Blob objects are shared between rows and between
   tables; `isBlobPathnameReferenced` stays the gate.
6. **`created_at` is never bumped.** It orders `/nina/about` and `/admin/photos`. Neither replacing
   a photograph nor adopting one is taking a new one.
7. **`description` stays private.** Invariant 5 of the shipped set: it is `glm-4.6v`'s text, its only
   consumer is Nina's prompt, and nothing under `components/` may read it.
8. **The runner-facing chat renders exactly as it does today** for every photograph that still has a
   message. This work is about which rows the COLLECTION holds and which rows survive a delete.
   *One deliberate exception, added at reconciliation:* the **session-delete confirmation** in
   `components/nina/SessionRow.tsx` changes, because it currently promises the photographs will be
   destroyed and phase 1 makes that false. A confirmation that over-states the loss is as wrong as
   one that under-states it. `MessageActionsSheet`'s message-delete copy is NOT touched — that
   behaviour is unchanged (Decisions, row 1) — and no bubble, gallery cell or viewer changes at all.
9. **A reference row is still a real photograph in the conversation.** `is_reference` excludes a row
   from `/admin/photos`; it must not hide it from a bubble, from `/nina/about`, or from
   `loadNinaContext`.

### Phase 3 — The backfill

**Satisfies:** R2, R3
**Owns:**
- `scripts/nina-chat-photo-dedupe.mjs` — dry-run by default, `--apply` to write, the
  `scripts/nina-memory-reap.mjs` precedent for its shape and its output. It stamps `is_reference =
  true` on (a) every chat row whose `pathname` or `blob_url` matches a `nina_avatars` row of the same
  user, and (b) every row but the oldest of each same-`pathname` group. **It deletes nothing** —
  invariant 2 — and it prints what it would change, per row, before it changes it.
- The `package.json` script entry, a `/.snapshots/` line in `.gitignore`, and one appended section
  in `lib/nina/.workflows/package_readme.md` — **this phase is the only writer of that readme in the
  set**, so there is no append order to negotiate.
- Tests over the classification, as pure functions on rows rather than against a database. This
  phase's suite is green with no database and regardless of whether `0009` has been applied
  anywhere, which is what lets the phase be green on its own.
- **The collection predicate, restated in exactly two places** — `isCollectionCandidate` and the
  `--apply` UPDATE's WHERE — plus two prose paragraphs in the script header and one in the readme.
  `readImages`' SELECT deliberately carries **no** predicate: the report's `not candidates` count and
  the `candidates === carryOvers + duplicates + keepers` invariant both need the rejected rows to
  arrive. This is the phase's one duplicated fact and its plan says out loud that a change to phase
  2's predicate must be followed in all five sites.

**Does not touch:** `lib/**` (except the prose readme), `app/`, `components/`, `drizzle/`,
`npm run db:generate`, `scripts/blob-reap.mjs`, and the suites phases 1 and 2 own. It introduces no
`DELETE`, no `del()`, and no `@vercel/blob` import.

**Exit criteria:** `format:check`, `lint`, `typecheck` and `test` green;
`npm run nina:chat-photo-dedupe` either prints the two classes and writes nothing, or refuses with
the missing-column message — and in neither case creates `.snapshots/`;
`grep -nEi 'delete|del\(|@vercel/blob' scripts/nina-chat-photo-dedupe.mjs` returns only prose. The
`--apply` run itself is an operator step after the branch lands, not part of this phase's
verification.

## Rollback

- **Phase 3** — nothing to roll back before `--apply`. After it: the stamps are recoverable from the
  `\copy` snapshot the script takes first, and `is_reference = false` restores the previous listing.
- **Phase 2** — revert the commit. The column stays and stays `false`, which is phase 1's state.
- **Phase 1** — revert the commit and `drizzle/0009_*`. Re-tightening `message_id` to `NOT NULL`
  **fails while orphaned rows exist**, so a rollback after any session has been deleted needs those
  rows re-parented or removed first. Say so out loud rather than discovering it on a bad night.
- **As a whole** — the branch is not merged until every phase is green; `main` is unaffected until
  then.
