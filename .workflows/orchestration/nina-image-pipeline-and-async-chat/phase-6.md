# Phase 6: Permanent session deletion: take the distilled memory with it

**Plan set:** `NINA_IMAGE_PIPELINE_AND_ASYNC_CHAT_PLAN.md`
**Analysis:** `20260906-204533-IMG9_code_analyzer.md`
**Satisfies:** R8 — "make sure deleted chat sessions are deleted permanently from the db … the deleted sessions polluted nina character and it gets worse as time goes on"
**Depends on:** none
**Difficulty:** NORMAL
**Package:** `lib/nina`

---

## Goal

After this phase, deleting a chat session also deletes every distilled memory row that conversation
produced — the ledger facts, the standing slots, and the individual pending promises she made in it
— in the **same transaction** as the session delete, so there is no window in which one lands and
the other does not. A one-off script reaps the rows that are already orphaned. And the three places
in the tree that currently assert the *opposite* design in prose (`lib/db/schema.ts:841-848`,
`lib/nina/queries.ts:810-820`, `lib/nina/sessionActions.ts:181-188`) are rewritten to record the
override rather than leaving the next reader to conclude it was forgotten.

Nothing else in the tree changes. No migration, no new column, no foreign key.

---

## The decision, and why it is (a) and not (b)

The plan index's Decisions table already settled *that* the memory is purged (rung 5: the user's raw
input overrides a code comment). This phase settles *how*, and the scope brief named two candidates.

**Chosen: (a) — purge in the same transaction as the session delete, joining `source_message_id`
against the messages the cascade is about to remove.**

Three reasons, in the order that decides it:

1. **A foreign key cannot tell a deleted *sentence* from a deleted *conversation*, and the
   difference is the whole requirement.** `ON DELETE CASCADE` on `source_message_id` would also fire
   from `deleteNinaMessage` (`lib/nina/queries.ts:1182`), where the shipped argument is still
   correct and nobody asked for a change: *"a distilled fact may be true after the sentence that
   produced it is gone"*. R8 is not about a sentence. Deleting a whole session is the runner saying
   *this topic never happened*; deleting one bubble is him tidying one line. (a) overrides exactly
   one of those and leaves the other alone. (b) cannot express that distinction at all.
2. **(b) cannot be added by a generated migration against the live database.** `ALTER TABLE … ADD
   CONSTRAINT … FOREIGN KEY` is validated against existing rows, and there are already dangling
   pointers in production (see §Audit, item 1). `npm run db:generate` emits the bare `ALTER` and
   nothing else, so `npm run db:migrate` would fail on the first run. Making (b) work means
   hand-writing a pre-clean `DELETE` into a generated migration file — which is precisely the class
   of edit invariant 10 exists to discourage.
3. **(b) would also reach rows the admin asserted.** `lib/admin/memoryStore.ts:112-131`'s
   `adminUpdateFact` re-labels an edited row `source = 'admin', source_message_id = NULL` *in one
   statement* so that "the pointer stops being a lie" — but only for rows an admin has actually
   touched. Under (a) the pointer-membership test (`source_message_id IN (…)`) can never match a
   NULL, so the admin-row guarantee (R24) is preserved **structurally** rather than by an extra
   `source <> 'admin'` predicate that someone could later drop.

The (a) hazard the brief named — *"must read the message ids BEFORE the cascade removes them"* — is
answered without a pre-read: the purge statements use a **correlated subquery** over `nina_messages`
and run **inside the same `db.batch` transaction, before** the `DELETE FROM nina_chat_sessions`. The
rows are still there when the subquery is evaluated. This is strictly better than reading ids into
TypeScript first, because it also closes the read-then-write window in which a concurrent send could
file a new message into the session being deleted.

**No migration is generated by this phase**, and that is a decision rather than an omission.
**RECONCILED, and it is stronger than it looks: no migration is generated by ANY phase in this
set.** The index's draft treated this phase as the set's migration owner, and two other phases were
written pointing at it — phase 3 deferred a unique index for `openNinaChatTurn` to "phase 6's
migration", and phase 1 said "phase 6's generated migration is the only migration in the set".
Neither pointer had anything on the other end. Both have been corrected: phase 3 now accepts its
race permanently (it is bounded to two *different* clients inside ~50 ms, and costs one duplicate
reply), and phase 1 says plainly that there is none. **`drizzle/` gains no file and
`npm run db:check` must be clean at the end of every phase**, which makes the check below a
whole-set invariant rather than this phase's local one. The reasons:

- No FK is added (see above).
- No index is added. The subquery is `WHERE user_id = $1 AND session_id = $2` on `nina_messages`,
  which reads `nina_messages_session_seq_idx` (`lib/db/schema.ts:922`) — the index that already
  exists *specifically so that "every `removeNinaSession` would sequentially scan the entire
  conversation"* does not happen. The outer deletes scan `nina_memory_facts` (13 rows) and
  `nina_memory_slots` (6 rows), on a statement that runs only when a human presses a delete
  control. An index on `source_message_id` would be a migration bought for a sequential scan of a
  table that fits in one page. **The trigger that would change this answer:** if `nina_memory_facts`
  ever passes ~50 k rows *and* session deletion becomes something other than a manual gesture.

`npm run db:check` must still pass, unchanged, and `drizzle/` gains no file.

### Things that survive but do **not** reach `loadNinaContext` — checked and dismissed

- **`nina_message_images`** — **cascades, confirmed.** `nina_message_images.message_id` is
  `references(() => ninaMessages.id, { onDelete: 'cascade' })`; `tests/db.schema.nina.test.ts:147`
  and `:345` already assert it. Postgres chains `nina_chat_sessions` → `nina_messages` →
  `nina_message_images` from one DELETE. **The Blob bytes are not deleted** — out of scope, the
  `reap-orphaned-blobs` skill's card owns `nina/`, and the plan index's Scope section says so.
- **`nina_messages.reply_to_id`, `ON DELETE SET NULL`, across a session boundary** — confirmed
  harmless and confirmed non-blocking. `SET NULL` never refuses a delete, so the cascade cannot
  deadlock on it. A surviving message in *another* session that quoted a message in the deleted one
  has its pointer nulled, and `lib/nina/reply.ts`'s `resolveQuote` already documents a null pointer
  as "render it as a plain message". No new behaviour, and it is asserted at
  `lib/nina/queries.ts:1160-1163`. (In practice cross-session quoting is rare — `replyToId` is
  normally same-session — but the degradation is correct either way.)
- **`nina_turns`, `kind='chat'` and `kind='image'` alike** — **leave, deliberately.** The table has
  no `session_id` column and no FK to `nina_messages` (its `args` jsonb carries `replyToId` as a
  plain string). It is the audit trail and the money ledger; invariant 9 requires
  `cost_micro_usd` to survive. Nothing in `loadNinaContext` reads it. See the Phase 4 contract above.
- **`hasProactiveMessageForRun`** (`queries.ts:1208`) — this is a *proactive marker*, and it is
  stored as a `nina_messages` row (`source='run_committed' AND run_id=…`), so it **cascades away
  with the session**. Consequence, named rather than discovered: deleting the session that holds her
  reaction to a run makes that run eligible for a proactive reaction again. That is the correct
  outcome — the reaction no longer exists, so re-reacting is not a duplicate — and it needs no code.
- **`nina_nags`** — see row 7.
- **`nina_folders`, `nina_tuning`, `push_subscriptions`** — no conversational content, no message
  pointer, not read per-session.
- **The `name` slot** — the one *residue* this phase knowingly leaves. `lib/nina/memory.ts:1247`
  writes it with `sourceMessageId: null` on purpose (it is bookkeeping derived from identity plus
  the nickname), so the purge cannot reach it, and it may still embed a nickname whose own slot was
  just purged. It self-heals: `planMemoryWrites` recomputes it on the very next distillation from
  whatever `identity.nickname` then is. Special-casing it would mean the purge grew a list of key
  names, which is the thing that goes stale.

### The accepted cost, stated plainly

If the runner's nickname was established in the session he deletes, **she forgets it** until he says
it again. Same for any standing slot (`running_days`, what he is training for, what hurts) first
learned there. That is the requirement working, not a bug: his words are *"the deleted sessions
polluted nina character"*, and a slot distilled from a conversation he chose to erase is exactly
that. The escape hatch already exists and should be named in the docstring: a fact or slot asserted
through `/admin/memory` is written `source = 'admin', source_message_id = NULL` and is therefore
**structurally immune** to this purge.

### Does Phase 3 affect this?

Yes, and it is a **handoff, not a dependency**. Phase 3 moves `runTurnDistillation`
(`lib/nina/distill.ts:350` — the writer of the very rows purged here) out of the request's `after()`
and into a durable background task. That widens an already-existing race: send a message, delete the
session, and a distillation that completes afterwards writes facts stamped with a
`source_message_id` that no longer exists — re-creating the orphan class this phase just purged.
The race exists today (the `after()` window is short but real); Phase 3 lengthens it. Closing it
belongs to Phase 3 — see §Handoffs. It changes nothing about this phase's mechanism, and
`npm run nina:memory-reap` is the standing backstop either way.

### Step 2: `lib/nina/queries.ts` — `removeNinaSession` becomes the four-statement purge

**File:** `lib/nina/queries.ts:803-834` (the JSDoc block and the function body — replace both in
full)
**Change:** one `DELETE` becomes one `db.batch` of four statements, ordered so that the three purges
run while the messages still exist and the session delete runs last. `db.transaction()` throws on
the `neon-http` driver (`lib/db/index.ts:8-11`); `db.batch([...])` *is* the transaction, and it is
one HTTP round trip.

**Code — the complete replacement for lines 803-834:**

```ts
/**
 * **R11's delete, and R8's purge, in one transaction.**
 *
 * `nina_chat_sessions` -> `nina_messages.session_id` (cascade) -> `nina_message_images.message_id`
 * (cascade, and it predates this feature). Postgres chains both, so the last statement below
 * removes the conversation and its photo ROWS.
 *
 * ── THE THREE STATEMENTS IN FRONT OF IT, AND WHY THEY EXIST (R8) ──────────────────────────────
 * This function used to be one DELETE, and its own comment argued that the memory ledger should
 * survive it: *"a distilled fact can be true after the sentence that produced it is gone"*. That
 * argument is still correct about a SENTENCE and it is still what `deleteNinaMessage` does. It is
 * wrong about a CONVERSATION, and the runner measured it: *"the deleted sessions polluted nina
 * character and it gets worse as time goes on"*. `loadNinaContext` reads the session's message
 * window and THE WHOLE RELATIONSHIP'S memory ledger — the window is scoped, the ledger is not — so
 * the ledger was the only surviving channel by which a deleted session still reached her prompt.
 * Deleting a session is him saying the topic never happened; deleting one bubble is him tidying one
 * line. This function overrides the first and leaves the second exactly as it was.
 *
 * ── WHY A SUBQUERY AND NOT A PRE-READ ─────────────────────────────────────────────────────────
 * The purge has to name the messages the cascade is about to destroy, which means reading them
 * BEFORE the DELETE. A pre-read would do it, and would open a window in which a concurrent send
 * files a new message into the session between the read and the delete — a message whose distilled
 * facts would then survive. `db.batch` runs the whole array inside ONE transaction in array order,
 * so `sessionMessageIds` below is evaluated three times against rows that are still there, and
 * there is no window at all.
 *
 * ── WHY NOT A FOREIGN KEY WITH `ON DELETE CASCADE` ────────────────────────────────────────────
 * Three reasons, and the first is the one that decides it. (1) An FK fires from
 * `deleteNinaMessage` too, and cannot tell a deleted sentence from a deleted conversation. (2) It
 * cannot be added by a generated migration while dangling rows exist, and they do —
 * `npm run nina:memory-reap` is the one-off that clears them. (3) The membership test below can
 * never match `source_message_id IS NULL`, which is how `/admin/memory` writes and re-labels every
 * hand-asserted row (`lib/admin/memoryStore.ts`) — so R24's admin-row guarantee holds
 * STRUCTURALLY here, rather than through a `source <> 'admin'` predicate somebody could drop. An
 * admin-asserted fact is the runner's way to make a memory immune to this purge.
 *
 * **What it STILL deliberately leaves behind:**
 *   - the Blob objects those image rows pointed at. The rows go, the bytes stay — the same call
 *     `deleteNinaMessage` makes, and the `reap-orphaned-blobs` skill does not cover the `nina/`
 *     prefix yet. This function does NOT pre-read the image rows to hand their pathnames back: a
 *     return value nothing consumes is a promise this set has not made.
 *   - `nina_turns`. It is the audit trail and the money ledger; a removed conversation does not
 *     un-spend its tokens (plan invariant 9). A job's `args.replyToId` may afterwards name a
 *     message that no longer exists, which is the same degradation a deleted message already
 *     produces, in bulk.
 *   - `nina_nags` and `nina_avatars`. A nag records what she has said about a TRAINING pattern and
 *     carries no message pointer; an avatar is her face. Neither is a conversation.
 *   - the `name` slot, whose `source_message_id` is null by design (`lib/nina/memory.ts`) because
 *     it is derived bookkeeping. It is recomputed on the next distillation.
 *
 * A surviving message in ANOTHER session that quoted one of these has its `reply_to_id` set to NULL
 * by the self-FK, and `resolveQuote` already degrades that to plain text. `SET NULL` never blocks a
 * delete, so it cannot deadlock the cascade. No new behaviour.
 *
 * `false` is "not yours, or already gone" — the caller turns that into one message. When it is
 * false, the three purge statements have already selected nothing: `sessionMessageIds` carries
 * `user_id` in its own WHERE beside `session_id` (rule 1), so a foreign or stale id yields an empty
 * set rather than somebody else's message ids.
 */
export async function removeNinaSession(userId: string, id: string): Promise<boolean> {
  /* The messages this session is about to lose. A subquery, not a value — see the header, and see
   * `getRunByShareToken` in `lib/db/queries.ts`, which builds a correlated subquery exactly this
   * way and for the neighbouring reason: *"so the child selects are filtered by the token itself
   * rather than by a run id the caller could have supplied. All five statements share one
   * snapshot."* Here it is a session id rather than a token, and the snapshot is what makes the
   * purge and the delete indivisible. */
  const sessionMessageIds = db
    .select({ id: ninaMessages.id })
    .from(ninaMessages)
    .where(and(eq(ninaMessages.userId, userId), eq(ninaMessages.sessionId, id)))

  /* The `pending_promises` entries that came from this conversation, as a predicate over the slot's
   * jsonb array. Spelled once and used twice: once to decide whether the row needs rewriting at
   * all, and once (inverted) to decide which entries survive the rewrite. */
  const promisesFromThisSession = sql`
    select 1
      from jsonb_array_elements(${ninaMemorySlots.value} -> 'promises') as t(entry)
     where t.entry ->> 'sourceMessageId' in (
             select ${ninaMessages.id}
               from ${ninaMessages}
              where ${ninaMessages.userId} = ${userId}
                and ${ninaMessages.sessionId} = ${id}
           )
  `

  const [, , , removed] = await db.batch([
    /* 1. The ledger rows distilled from this conversation. `source_message_id IS NULL` can never
     *    match an `IN`, which is exactly the admin-row guarantee. */
    db
      .delete(ninaMemoryFacts)
      .where(
        and(
          eq(ninaMemoryFacts.userId, userId),
          inArray(ninaMemoryFacts.sourceMessageId, sessionMessageIds),
        ),
      ),

    /* 2. The standing slots this conversation set — his nickname, his usual running days, what he
     *    is training for. `pending_promises` is EXCLUDED and handled by statement 3: it is one row
     *    holding a LIST, so dropping the row over one entry would cancel every promise she has
     *    outstanding, including the ones she made in conversations he kept. */
    db
      .delete(ninaMemorySlots)
      .where(
        and(
          eq(ninaMemorySlots.userId, userId),
          ne(ninaMemorySlots.key, NINA_SLOT_PENDING_PROMISES),
          inArray(ninaMemorySlots.sourceMessageId, sessionMessageIds),
        ),
      ),

    /* 3. `pending_promises`, pruned entry by entry rather than row by row.
     *
     *    The ROW's own `source_message_id` is not usable for this and it is worth saying why:
     *    `lib/nina/promises.ts`'s sweep rewrites the slot through `upsertNinaMemorySlot` WITHOUT a
     *    `sourceMessageId`, which defaults the column to NULL — so after the first sweep the row
     *    points at nothing while its entries still point at real messages. The entries are the
     *    provenance; the row is not.
     *
     *    `jsonb_typeof(... ) = 'array'` is a guard and not decoration: without it, a malformed slot
     *    value would make `jsonb_array_elements` yield zero rows, `jsonb_agg` return NULL, and the
     *    coalesce rewrite the row to an empty promise list — destroying data on the way past. With
     *    it, a malformed row is left exactly as it is, for a human to look at.
     *
     *    The `exists` in the WHERE means this statement is a no-op — no write, no `updated_at`
     *    bump, nothing in `/admin/memory`'s "updated" column — unless this session actually
     *    produced one of the promises. */
    db
      .update(ninaMemorySlots)
      .set({
        value: sql`
          jsonb_build_object(
            'promises',
            coalesce(
              (
                select jsonb_agg(t.entry order by t.ord)
                  from jsonb_array_elements(${ninaMemorySlots.value} -> 'promises')
                       with ordinality as t(entry, ord)
                 where t.entry ->> 'sourceMessageId' is null
                    or t.entry ->> 'sourceMessageId' not in (
                         select ${ninaMessages.id}
                           from ${ninaMessages}
                          where ${ninaMessages.userId} = ${userId}
                            and ${ninaMessages.sessionId} = ${id}
                       )
              ),
              '[]'::jsonb
            )
          )
        `,
        /* Written explicitly for the reason `upsertNinaMemorySlot` gives: `$onUpdate` and
         * `defaultNow()` fire on different paths, and a caller comparing two slots' `updated_at`
         * should be comparing like with like. */
        updatedAt: new Date(),
      })
      .where(
        and(
          eq(ninaMemorySlots.userId, userId),
          eq(ninaMemorySlots.key, NINA_SLOT_PENDING_PROMISES),
          sql`jsonb_typeof(${ninaMemorySlots.value} -> 'promises') = 'array'`,
          exists(promisesFromThisSession),
        ),
      ),

    /* 4. And only now the session itself, so the three statements above still had messages to join
     *    against. `RETURNING` is what makes ownership a fact rather than a claim. */
    db
      .delete(ninaChatSessions)
      .where(and(eq(ninaChatSessions.userId, userId), eq(ninaChatSessions.id, id)))
      .returning({ id: ninaChatSessions.id }),
  ])

  return removed.length > 0
}
```

**Impact:**

import { afterEach, beforeEach, describe, expect, it, vi } from 'vitest'

/**

 * permanently from the db … the deleted sessions polluted nina character and it gets worse as time
 * goes on"*, and the subtlety is that the session delete was ALREADY a hard delete: what survived
 * was the distilled memory ledger, which `loadNinaContext` reads globally on every turn.
 *
 * So the property under test is not "a DELETE was issued". It is:
 *
 *   1. the purge and the delete are ONE transaction (`db.batch` — `db.transaction()` throws on the
 *      neon-http driver), so neither can land without the other;
 *   2. the session DELETE is LAST, because the three purges join against messages that the cascade
 *      is about to destroy — get this order wrong and the purge silently matches nothing, which is
 *      exactly the failure that ships green;
 *   3. every statement carries `user_id`, including both subqueries (plan invariant 5);
 *   4. `pending_promises` is pruned per ENTRY, never dropped as a row.

 * Asserted against generated SQL rather than against a spy, because a spy cannot tell (2) from a
 * batch in the wrong order.

type Queries = typeof import('@/lib/nina/queries')

let fake: FakeDb
let q: Queries

beforeEach(async () => {
  vi.resetModules()
  fake = installFakeDb()
  q = await import('@/lib/nina/queries')

afterEach(() => {
  uninstallFakeDb()
  vi.resetModules()
})

async function purge(userId = 'u1', sessionId = 'sessionAAAAA') {

  return { removed, sql: fake.queries.map((query) => query.sql) }

describe('removeNinaSession — one transaction, four statements, session last', () => {

  it('selects the message ids through a subquery that carries BOTH predicates', async () => {

      expect(statement).toContain('from "nina_messages"')
      expect(statement).toContain('"session_id" = $')
      expect(statement).toContain('"nina_messages"."user_id" = $')

  })

 * Delete the distilled memory rows whose source message no longer exists — the backlog R8 leaves
 * behind, and the standing backstop for the race it cannot close.
 *
 *   npm run nina:memory-reap            # the dry run: reports, writes nothing
 *   npm run nina:memory-reap -- --apply

 * to it. The same line `scripts/backfill-record-keys.mjs` and `scripts/blob-reap.mjs` draw.
 *
 * ── WHAT IT IS FOR, AND WHEN IT STOPS BEING NEEDED ────────────────────────────────────────────
 * `lib/nina/queries.ts`'s `removeNinaSession` now purges a session's distilled memory in the same
 * transaction as the delete, so from R8 onwards no new orphan is created by a session delete. Two
 * classes of orphan remain:
 *
 *   1. **The backlog.** Every session deleted before R8 landed left its facts and slots behind.
 *      Those are the rows this script exists to clear, once.
 *   2. **The race.** `runTurnDistillation` writes facts stamped with a `source_message_id` AFTER
 *      the turn finishes. A session deleted in that window gets a fact written into it that the
 *      purge already ran past. The window is short today and gets longer when the turn moves into
 *      a background task. Run this script when Nina says something that sounds like a conversation
 *      that no longer exists.
 *
 * ── IT DELETES ONLY WHAT IS PROVABLY DANGLING ─────────────────────────────────────────────────
 * The predicate is an anti-join against `nina_messages` on a NON-NULL `source_message_id`. A row an
 * admin typed carries `source_message_id = NULL` (`lib/admin/memoryStore.ts`) and is therefore
 * outside the predicate entirely — not excluded by a rule that could be dropped, but unreachable.
 * A row whose message still exists is likewise unreachable. There is no time bound, no heuristic
 * and no model call: a pointer either resolves or it does not.
 *

 * person who owns the database. And the question it asks — "does this message id exist" — has no
 * user in it, the same argument `nina_messages_session_seq_idx` makes for leading with
 * `session_id`. `user_id` is REPORTED on every row so the output is still readable per account.
 *
 * ── 'pending_promises' IS SPELLED HERE, AND THAT IS THE ONE DUPLICATED FACT ───────────────────
 * The authority is `NINA_SLOT_PENDING_PROMISES` in `lib/db/schema.ts`. That module cannot be

const url = process.env.DATABASE_URL
if (!url) {

  process.exit(1)

console.log(`${apply ? 'APPLY' : 'DRY RUN'} — reaping memory rows whose source message is gone\n`)

/* ── 1. the append-only ledger ──────────────────────────────────────────────────────────────── */

  select s.user_id, s.key, s.value, s.source, s.source_message_id, s.updated_at
    from nina_memory_slots s
   where s.key <> ${PENDING_PROMISES}
     and s.source_message_id is not null
     and not exists (select 1 from nina_messages m where m.id = s.source_message_id)

## Handoffs

**To Phase 3 (R6, `lib/nina/actions.ts`) — the distillation race. NAMED HERE, ACCEPTED AND OWNED
THERE.**
Phase 3 moves `runTurnDistillation` out of `after()` and into a durable background task. That
lengthens an existing window: if the runner deletes a session while a turn's distillation is still
in flight, the distillation writes `nina_memory_facts` / `nina_memory_slots` rows stamped with a
`source_message_id` that no longer exists — re-creating exactly the orphan class this phase purges.
**This phase deliberately does not close it**, because every available fix lives in a file Phase 3
owns, and the alternative (making `appendNinaMemoryFacts` verify the pointer on every insert) would
put a read in front of every memory write, including the admin path where the pointer is
legitimately NULL. The cheap fix is Phase 3's: **have the background turn check that its session row
still exists before persisting, and abandon the turn if it does not** — the same check already
protects it from writing bubbles into a conversation that is gone.

**RECONCILED: phase 3 has taken it.** Its plan now carries **Step 6d**, which adds
`ninaSessionExists(userId, sessionId)` to `lib/nina/chatturn.ts` and guards both the persist point
and the chain, closing the turn as `error_code = 'session-gone'`. The window this phase widened from
milliseconds to up to 240 seconds is therefore closed at the source, in the phase that opened it.
Two things follow, and both matter:

- **Phase 3 does NOT depend on this phase, and must not be made to.** Its guard is correct on its
  own terms with or without the purge — writing Nina's bubbles, her distilled facts or a session
  title into a conversation the runner has deleted is wrong regardless of who cleans up afterwards.
  The two phases still share no edge and can still run concurrently.
- **`npm run nina:memory-reap` remains the standing backstop, not a superseded one.** Phase 3's
  guard is a check-then-write and cannot be atomic against a delete landing in the microseconds
  between them; this script is what catches that, and its own header (§2, "the race") already says
  so. Belt and braces; neither is doing the other's job. Phase 3's Step 6d cross-references this
  script by name for the same reason.

**To Phase 4 (R1, `lib/nina/imagejobs.ts` and `app/nina/jobs/*`) — the degradation contract.**
Published above under Interface Contract. In one line: **`nina_turns` is untouched by a session
delete**, so every job still appears on `/nina/jobs` with its full cost and error history; what
breaks is only the resolution of `args.replyToId` to a live message and thence to a session. Phase 4
should treat "the triggering message is gone" and "the session was removed" as one state, because
after this phase they are: the session delete cascades to the message, so there is no case where the
message survives and the session does not.

**Left for the `reap-orphaned-blobs` card (already scoped out by the plan index).**
The Vercel Blob objects behind cascaded `nina_message_images` rows. This phase changes nothing about
them and its docstrings continue to say so. Now that image rows can vanish in bulk when a session is
deleted, that card is worth more than it was.

**Not done, and not a defect: `deleteNinaMessage` is unchanged.**
Deleting a single message still leaves its distilled facts, per assumption A5. That is the position
the schema comment argues, it is correct about a sentence, and R8 does not reach it. If the runner
later reports the same pollution from single-message deletes, the mechanism is already here — add
the same two `IN (SELECT …)` deletes to `deleteNinaMessage`'s batch — but it is a separate card and
a separate requirement.

**Drive-by cleanups noticed and deliberately not taken.**
`lib/nina/queries.ts:1160-1180`'s `deleteNinaMessage` header also carries the old "left DANGLING"
argument. It is *still true of that function*, so it needs no edit — only the three places where the
prose describes a **session** delete were rewritten.

## Rollback

This phase is one commit and reverts cleanly on its own:

```
git revert <phase-6-commit>
```

There is no migration, no schema change and no data migration, so a revert restores the previous
behaviour completely — `removeNinaSession` goes back to its single DELETE and the ledger goes back to
surviving. The only irreversible part is the data the reap script deleted with `--apply`, which is by
construction rows whose provenance no longer resolved; there is no undo and none is wanted (that is
the same "no archive flag, no undo" stance assumption A8 takes for the session itself). Take a
snapshot of `nina_memory_facts`, `nina_memory_slots` and the `pending_promises` slot before the first
`--apply` if the 13 rows are worth keeping:

```
psql "$DATABASE_URL" -c "\copy (select * from nina_memory_facts) to 'facts-backup.csv' csv header"
psql "$DATABASE_URL" -c "\copy (select * from nina_memory_slots) to 'slots-backup.csv' csv header"
```

The new script and the new test file can simply be deleted; nothing imports either.
