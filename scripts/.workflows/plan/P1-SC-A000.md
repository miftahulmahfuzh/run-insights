## Goal

After this phase, `npm run nina:shortcuts-import` reads every `nina_memory_facts` row, recognises
the four prose grammars the user has been writing shortcuts in, and reports exactly which rows are
shortcuts and which are genuine facts — writing nothing. With `--apply` it inserts the shortcuts
into `nina_shortcuts` idempotently on `(user_id, match_key)`; with `--apply --prune` it then deletes
the ledger rows it has confirmed are now shortcuts, by `nina_memory_facts.id`. The scenes the user
typed by hand into the wrong table reach the right one without him retyping a character, and the
genuine facts are provably untouched. **How many there are is whatever the live table yields** — see
D3.

## Decisions taken in this plan, with the measurement behind each

### D1. The script IMPORTS phase 1's matcher. It does not re-implement it.

The brief this planner was handed asserted that *"a `.mjs` script cannot import
`lib/nina/shortcuts.ts`"* and asked for a hand-written second implementation guarded by a parity
test. **That assertion is false for this repo, and it was measured, not assumed.**

> **Accepted at reconciliation, and it is now the set's position rather than this phase's
> deviation.** The measurement was re-checked against the repo; phase 1's handoff to this phase has
> been rewritten to say "import, do not reimplement"; and the consequence has been propagated
> upward — invariant 4 in the plan index now states that `lib/nina/shortcuts.ts`'s zero-import rule
> is load-bearing for this script's BOOT and not only for the browser bundle. A drift class was
> eliminated rather than tested for, which is a better outcome than the brief asked for.

`scripts/nina-profpic.mjs` — a `.mjs` file — already does exactly this at `nina-profpic.mjs:151`:

```js
import { ID_LENGTH, newId } from '../lib/id.ts'
import { NINA_BLOB_PREFIX } from '../lib/nina/images.ts'
import { NINA_IMAGE_CACHE_MAX_AGE, NINA_IMAGE_PATHNAME_RE } from '../lib/nina/imagerecipe.ts'
```

and its package.json entry (`package.json:32`) is
`node --experimental-strip-types --no-warnings --env-file=.env.local scripts/nina-profpic.mjs`.
`scripts/backfill-record-keys.mjs:85` does the same with `../lib/records/catalog.ts`. Node in this
worktree is **v22.23.1**, which supports `--experimental-strip-types`. A direct probe of the exact
shape phase 1 will produce — a zero-import `.ts` exporting a const, a type alias, an interface and
two functions, imported from a `.mjs` — ran clean:

```
$ node --experimental-strip-types --no-warnings use.mjs
OK 16 "✌" word
```

`nina-memory-reap.mjs`'s header explains the one case where this does **not** work — it cannot
import `lib/db/schema.ts` "because its imports are drizzle at runtime rather than `import type`".
That is precisely the condition plan-set invariant 4 forbids for `lib/nina/shortcuts.ts`. The
module is zero-import *by rule*, which makes it the single most importable file in the tree.

So the failure mode the brief was worried about — a second implementation of
`normalizeNinaTrigger` drifting from the first and writing a `match_key` the matcher can never
find, a silent total failure of the import — is not mitigated here. **It is made impossible.** A
parity test can only catch drift the day someone remembers to extend it; an import cannot drift at
all.

A build step was never a candidate: there is no build for `scripts/`, `npm test` does not run one,
and adding one to make a laptop-run maintenance script work would be a new piece of infrastructure
for a problem the runtime already solves.

**The guard is kept anyway, in a stronger form.** `tests/nina.shortcutsImport.test.ts` asserts
*function identity*:

```ts
expect(scriptNormalize).toBe(normalizeNinaTrigger)
```

This fails the instant anyone converts the import back into a copy. It was verified to hold: the
alias specifier `@/lib/nina/shortcuts` and the script's relative specifier
`../lib/nina/shortcuts.ts` resolve to the same absolute module id under this repo's
`vitest.config.ts`, so Vitest hands both importers the same function object. A behavioural parity
sweep over every real trigger is kept beside it, so the file still fails loudly rather than
cryptically if the identity assertion ever becomes the wrong question.

**Consequence for the package.json line:** it carries `--experimental-strip-types --no-warnings`,
following `nina:profpic` and `records:backfill` rather than `nina:memory-reap`. That is the
convention for a script that imports the app's TypeScript, and this script does.

### D2. Four grammars, tried in order, with the trigger group shaped per grammar.

The plan index's draft sketched the regexes as, e.g., `^\s*kalo|kalau\s+…`, and named three
grammars where the data has four. **That sketch was broken twice over:** an unparenthesised `|`
splits the whole pattern, so it reads `^\s*kalo` OR `kalau\s+…` — the second alternative unanchored,
the first matching any string that starts with "kalo"; and its C/D trigger group
(`^\s*(?<trigger>[\s\S]*?)\s*artinya`) is anchored but still matches
`kalo dia diem artinya dia marah` with a 13-character trigger, under `NINA_TRIGGER_MAX`, so the
length bound would not have saved it either.

**Settled at reconciliation: the four regexes below are the set's only definition of the grammars,
and the index now points here instead of restating a variant.** The corrections are `(?:kalo|kalau)`
for the alternation and `\S+?` for the C/D trigger group.

Grammars A and B allow whitespace inside the trigger, because five real triggers are Latin tokens
and one of them (`nom nom`) contains a space. Grammars C and D require `\S+?` — **no whitespace at
all** — and that is what satisfies the brief's "must not match a row that merely contains the word
*artinya* mid-sentence". Anchoring alone does not do it: `^\s*(?<trigger>[\s\S]*?)\s*artinya` is
anchored and still matches `kalo dia diem artinya dia marah` with a 13-character trigger, which is
under `NINA_TRIGGER_MAX` and would have imported garbage. `\S+?` cannot cross the space, so that
string reaches no grammar and is reported SKIPPED. Both that string and
`buat aku itu artinya dia sayang` are test cases.

Order is A → B → C → D, and **all four are tried**; the first `ok: true` wins. Stopping at the
first *structural* match would be wrong: the `🫦` row has the shape of A up to the verb, and only B
parses it correctly.

**Every one of the four regexes was run against the real production strings before this plan was
written.** 24 of 24 target rows parse to the expected trigger; all four genuine facts plus both
mid-sentence-`artinya` decoys reject. The verified results, grammar by grammar:

| Grammar | Triggers it captures in the real data |
|---|---|
| A (`… nina [harus] bilang …`) | `🍑` `💦` `💋` `🍆` `🤏` `🫴` `lick!` `nom nom` `yumm` `slurp!` `plak!` |
| B (`… nina bakal …`) | `🤤` `🫦` |
| C (`<T>artinya …`) | `🙌` `🫶` `🤝` `👐` `✌️` `🤲` `👏` `👌` |
| D (`<T>ini posisi …`) | `👍` `👎` `👊` |

The awkward real-world spacing all of it survives: `bilang🍑 ,` (no space before the trigger),
`🤏,` (no space after), `bilang: 🫦 ,` (a colon before the trigger), `✌️artinya` (trigger abutting
the keyword, and carrying `U+FE0F`), `🤲 artinya` (one space), and the `yumm` row where a **literal
newline** stands where a comma should be — handled by `\s*` rather than by a special case.

### D3. The exact number of importable rows is never hard-coded.

Not in the script, not in the test, not in the exit criteria, and not in the index. The count is
whatever the live table yields.

**The figures, settled at reconciliation and consistent across the index, the analysis and all four
plans: 24 shortcut-shaped rows at the time of the read — 19 emoji (one of them `✌️`, carrying
`U+FE0F`) and 5 Latin tokens — 4 genuine facts, grammar split 11 / 2 / 8 / 3.** The earlier
disagreement was a miscount: 19 is the EMOJI count, not the trigger count, and the
`artinya` / `ini posisi` families were tallied differently in two documents.

None of that is load-bearing, and that is the point. **The ledger is LIVE and it moved during the
analysis** — 28 rows at 18:45, 27 at 19:58, the user having deleted a fact in between. The numbers
above describe one afternoon; the script reports the number it found when it runs. The test asserts
*per string*, never a total, and `PROD_SHORTCUTS` / `PROD_FACTS` are fixtures of what production
held that day rather than a specification of what it holds now.

### D4. `--prune` deletes only a byte-identical row, and only by id.

For each candidate, prune re-reads `nina_shortcuts` for `(user_id, match_key)` and deletes the
ledger row **only if** a shortcut exists there and its `expansion` is byte-identical to the one
parsed out of that ledger row. If the operator has already rewritten the expansion on
`/admin/shortcuts`, the ledger row is **kept** and reported — deleting it would destroy the only
remaining copy of what he originally typed. He can remove it by hand on `/admin/memory`.

The delete is `where id = $1 and user_id = $2`, never a pattern, never a `like`, never a re-parse.

### D5. `"trigger"` is quoted in the raw SQL.

`TRIGGER` is non-reserved in PostgreSQL so an unquoted column name would work, but this script
writes production and hand-written SQL is the one place where "would work" is not worth checking.
Drizzle quotes it in phase 1's DDL; this script quotes it too.

### D6. The label is a placeholder and the script says so out loud.

`label` is the first 60 characters of the expansion, cut back to the last word boundary, with a
trailing lone surrogate stripped so a cut never lands inside an emoji's surrogate pair. The script
prints one line saying it is a placeholder for the operator to rewrite on `/admin/shortcuts`, and
the same statement is a comment on `placeholderLabel`. **The script never writes a description of
the scene it did not find in the data.**

**Transcription note for the implementing session:** the emoji in the header comment are literal
characters. Type them (or paste them) as characters. Do not convert them to `\uXXXX` escapes on the
way into the file and do not let a heredoc turn a backslash into a literal — a stray control
character in a source file makes `grep` treat it as binary and the next person will not find it.

**Code:**

```js
/**
 * Lift the shortcut-shaped rows out of `nina_memory_facts` into `nina_shortcuts`.
 *
 *   npm run nina:shortcuts-import                        # the dry run: reports, writes nothing
 *   npm run nina:shortcuts-import -- --apply
 *   npm run nina:shortcuts-import -- --apply --prune     # …and clear the ledger rows it wrote
 *   npm run nina:shortcuts-import -- --user <id> --limit 3
 *
 * NOT A TEST, and never part of `npm test`: it reads the real database and with `--apply` it writes
 * to it. The same line `scripts/nina-memory-reap.mjs` and `scripts/blob-reap.mjs` draw.
 *
 * ── WHAT IT IS FOR ────────────────────────────────────────────────────────────────────────────
 * Before `nina_shortcuts` existed the owner of this deployment had already been writing shortcuts
 * — trigger plus a long scene the trigger stands for — into the only writable surface he had,
 * `/admin/memory`. They are sitting in `nina_memory_facts` in four prose grammars, mislabelled
 * `category: 'person'`, capped at the newest 60 rows by `MEMORY_FACT_LIMIT`, and described to the
 * model as "colour, not structure". This script moves them to the table that was built for them.
 * It exists so he does not retype a single character of it.
 *
 * ── THE FOUR GRAMMARS, AND WHY THE TRIGGER GROUP DIFFERS BETWEEN THEM ─────────────────────────
 *   A   kalo|kalau (miftah|tah) bilang [:] <TRIGGER> [, or newline] nina [harus] bilang [:] <EXP>
 *   B   kalo|kalau (miftah|tah) bilang [:] <TRIGGER> [,]            nina bakal            <EXP>
 *   C   <TRIGGER> artinya    <EXP>
 *   D   <TRIGGER> ini posisi <EXP>
 *
 * A and B let the trigger contain whitespace: five of the real triggers are Latin tokens and one
 * of them is `nom nom`. C and D require `\S+?`, and that is load-bearing rather than tidy. A
 * lazy `[\s\S]*?` trigger in C is still anchored at ^ and still matches
 * `kalo dia diem artinya dia marah` with a 13-character trigger — under NINA_TRIGGER_MAX, so the
 * length check would not save it, and an ordinary sentence would have been imported as a
 * shortcut. `\S+?` cannot cross a space, so that sentence matches nothing and is reported.
 *
 * All four are tried and the first that parses cleanly wins. Stopping at the first STRUCTURAL
 * match would be wrong: the `🫦` row has A's shape up to the verb and only B reads it correctly.
 *
 * ── WHY THIS FILE IMPORTS lib/nina/shortcuts.ts INSTEAD OF RE-IMPLEMENTING IT ─────────────────
 * `match_key` is the only thing the runtime matcher looks at. A second implementation of
 * `normalizeNinaTrigger` that drifted by one character would write keys the matcher can never
 * find — an import that reports success and does nothing, which is the worst failure this script
 * has available. So it does not have a second implementation.
 *
 * `.mjs` importing the app's TypeScript is established practice here, not a new trick:
 * `scripts/nina-profpic.mjs` imports three `.ts` modules and `scripts/backfill-record-keys.mjs`
 * imports `lib/records/catalog.ts`, both under `--experimental-strip-types`. The one case where it
 * fails is documented in `nina-memory-reap.mjs`'s header: a module whose own imports are runtime
 * values (drizzle) rather than `import type`. `lib/nina/shortcuts.ts` has ZERO imports — the plan
 * set's invariant 4, held for a different reason (a client component needs the bounds) — so it is
 * the safest possible target. `lib/id.ts` is zero-import for the same kind of reason.
 *
 * IF A FUTURE CHANGE ADDS A RUNTIME IMPORT TO lib/nina/shortcuts.ts, THIS SCRIPT STOPS BOOTING.
 * That is the correct failure: loud, immediate, and at the top of the file.
 *
 * ── WHAT IT NEVER DOES ────────────────────────────────────────────────────────────────────────
 * It never deletes a ledger row that did not parse. It never deletes by pattern — only by
 * `nina_memory_facts.id`, and only after re-reading `nina_shortcuts` and finding a byte-identical
 * expansion there. It never invents a label: `label` is a slice of the operator's own words,
 * announced as a placeholder, for him to rewrite on /admin/shortcuts.
 */
import { pathToFileURL } from 'node:url'

import { neon } from '@neondatabase/serverless'

import { newId } from '../lib/id.ts'
import {
  NINA_SHORTCUT_EXPANSION_MAX,
  NINA_SHORTCUT_LABEL_MAX,
  NINA_TRIGGER_MAX,
  classifyNinaTrigger,
  normalizeNinaTrigger,
} from '../lib/nina/shortcuts.ts'

/* Re-exported so `tests/nina.shortcutsImport.test.ts` can assert FUNCTION IDENTITY against the
 * same two names imported from '@/lib/nina/shortcuts'. `toBe` on those is the anti-drift guard:
 * it fails the moment anyone turns this import back into a copy. */
export { classifyNinaTrigger, normalizeNinaTrigger }

export const USAGE =
  'usage: node --experimental-strip-types --no-warnings --env-file=.env.local ' +
  'scripts/nina-shortcuts-import.mjs [--apply] [--prune] [--user <id>] [--limit <n>]'

/** The label is cut here, at a word boundary. See `placeholderLabel`. */
export const LABEL_TARGET_CHARS = 60

/**
 * The four grammars, anchored, case-insensitive, Unicode-aware. Tried in this order.
 *
 * `\s*` between every part is what absorbs the real data's spacing: `bilang🍑 ,` with no space
 * before the trigger, `🤏,` with none after, `bilang: 🫦 ,` with a colon in front, `🤲 artinya`
 * with one space and `✌️artinya` with none, and the `yumm` row where a literal NEWLINE stands
 * where the comma should be.
 */
export const GRAMMARS = [
  {
    name: 'A',
    re: /^\s*(?:kalo|kalau)\s+(?:miftah|tah)\s+bilang\s*:?\s*(?<trigger>[\s\S]*?)\s*,?\s*nina\s+(?:harus\s+)?bilang\s*:?\s*(?<expansion>[\s\S]+)$/iu,
  },
  {
    name: 'B',
    re: /^\s*(?:kalo|kalau)\s+(?:miftah|tah)\s+bilang\s*:?\s*(?<trigger>[\s\S]*?)\s*,?\s*nina\s+bakal\s+(?<expansion>[\s\S]+)$/iu,
  },
  { name: 'C', re: /^\s*(?<trigger>\S+?)\s*artinya\s+(?<expansion>[\s\S]+)$/iu },
  { name: 'D', re: /^\s*(?<trigger>\S+?)\s*ini\s+posisi\s+(?<expansion>[\s\S]+)$/iu },
]

/* ── Pure helpers. These four are what `tests/nina.shortcutsImport.test.ts` proves. ────────── */

/**
 * Parse argv. Throws on anything ambiguous rather than picking a default, because the only
 * defaults available here are defaults that write production.
 */
export function parseArgs(argv) {
  const flags = { apply: false, prune: false, user: null, limit: null }
  for (let i = 0; i < argv.length; i++) {
    const arg = argv[i]
    if (arg === '--apply') {
      flags.apply = true
    } else if (arg === '--prune') {
      flags.prune = true
    } else if (arg === '--user') {
      const value = argv[++i]
      if (!value || value.startsWith('-')) throw new Error('--user needs a user id')
      flags.user = value
    } else if (arg === '--limit') {
      const value = Number(argv[++i])
      if (!Number.isInteger(value) || value < 1) {
        throw new Error('--limit needs a positive integer')
      }
      flags.limit = value
    } else if (arg === '--help' || arg === '-h') {
      throw new Error(USAGE)
    } else {
      throw new Error(`unknown argument ${arg}\n${USAGE}`)
    }
  }
  if (flags.prune && !flags.apply) {
    throw new Error(
      '--prune is only valid together with --apply: there is nothing to prune until the\n' +
        'shortcuts exist in nina_shortcuts. Re-run with --apply --prune.',
    )
  }
  return flags
}

/** A slice can land between the two halves of an emoji. Drop a dangling high surrogate. */
const dropLoneSurrogate = (value) => (/[\uD800-\uDBFF]$/.test(value) ? value.slice(0, -1) : value)

/**
 * The `label` an imported row gets: the operator's own first ~60 characters, cut back to the last
 * word boundary.
 *
 * IT IS A PLACEHOLDER. The script says so in its output too. `/admin/shortcuts` is where he
 * rewrites it into a name for the scene; this function's job is to never invent one.
 */
export function placeholderLabel(expansion) {
  const flat = expansion.replace(/\s+/g, ' ').trim()
  if (flat.length <= LABEL_TARGET_CHARS) return flat
  const cut = flat.slice(0, LABEL_TARGET_CHARS)
  const space = cut.lastIndexOf(' ')
  const label = dropLoneSurrogate((space > 0 ? cut.slice(0, space) : cut).trim())
  const fallback = dropLoneSurrogate(flat.slice(0, NINA_SHORTCUT_LABEL_MAX))
  return label.length > 0 ? label : fallback
}

/**
 * One ledger row -> a shortcut, or a reason it is not one.
 *
 * Every grammar is tried; the first that parses AND validates wins. A row that matched a grammar
 * structurally but failed a bound is reported with that bound named, rather than being silently
 * imported under a garbage key or silently dropped.
 */
export function parseShortcutRow(text) {
  if (typeof text !== 'string' || text.trim().length === 0) {
    return { ok: false, reason: 'the row is empty' }
  }
  let firstFailure = null
  for (const { name, re } of GRAMMARS) {
    const match = re.exec(text)
    if (!match?.groups) continue

    const trigger = match.groups.trigger.trim()
    const expansion = match.groups.expansion.trim()
    const fail = (reason) => {
      firstFailure ??= { ok: false, reason: `[${name}] ${reason}` }
    }

    if (trigger.length === 0) {
      fail('the trigger is empty')
      continue
    }
    if (expansion.length === 0) {
      fail('the expansion is empty')
      continue
    }
    const matchKey = normalizeNinaTrigger(trigger)
    if (matchKey.length === 0) {
      fail(`the trigger ${JSON.stringify(trigger)} normalises to nothing`)
      continue
    }
    if (matchKey.length > NINA_TRIGGER_MAX) {
      fail(
        `the trigger is ${matchKey.length} chars, the ceiling is ${NINA_TRIGGER_MAX}: ` +
          JSON.stringify(trigger.slice(0, 40)),
      )
      continue
    }
    if (expansion.length > NINA_SHORTCUT_EXPANSION_MAX) {
      fail(
        `the expansion is ${expansion.length} chars, the ceiling is ${NINA_SHORTCUT_EXPANSION_MAX}`,
      )
      continue
    }
    return {
      ok: true,
      grammar: name,
      trigger,
      expansion,
      matchKey,
      kind: classifyNinaTrigger(matchKey),
    }
  }
  return firstFailure ?? { ok: false, reason: 'no grammar matched — this is a fact, not a shortcut' }
}

const clip = (value, n) => {
  const flat = value.replace(/\s+/g, ' ').trim()
  return flat.length > n ? `${dropLoneSurrogate(flat.slice(0, n - 1))}…` : flat
}

async function main() {
  let flags
  try {
    flags = parseArgs(process.argv.slice(2))
  } catch (error) {
    console.error(error.message)
    process.exit(2)
  }

  if (!process.env.DATABASE_URL) {
    console.error('DATABASE_URL is not set. Run with `node --env-file=.env.local`.')
    process.exit(2)
  }
  const sql = neon(process.env.DATABASE_URL)

  const mode = flags.apply ? (flags.prune ? 'APPLY + PRUNE' : 'APPLY') : 'DRY RUN'
  console.log(`${mode} — lifting shortcuts out of nina_memory_facts into nina_shortcuts`)
  if (flags.user) console.log(`  user filter    ${flags.user}`)
  if (flags.limit !== null) console.log(`  limit          ${flags.limit} importable row(s)`)
  console.log('')

  const facts = flags.user
    ? await sql`
        select id, user_id, text, created_at
          from nina_memory_facts
         where user_id = ${flags.user}
         order by created_at
      `
    : await sql`
        select id, user_id, text, created_at
          from nina_memory_facts
         order by user_id, created_at
      `

  /* ── 1. read the ledger and sort it into shortcuts and facts ────────────────────────────── */

  const candidates = []
  const skipped = []
  const seen = new Set()

  for (const row of facts) {
    const result = parseShortcutRow(row.text)
    if (!result.ok) {
      skipped.push({ factId: row.id, userId: row.user_id, text: row.text, reason: result.reason })
      continue
    }
    const dedupeKey = `${row.user_id}::${result.matchKey}`
    if (seen.has(dedupeKey)) {
      skipped.push({
        factId: row.id,
        userId: row.user_id,
        text: row.text,
        reason: `an earlier ledger row already defines ${JSON.stringify(result.trigger)}`,
      })
      continue
    }
    seen.add(dedupeKey)
    candidates.push({
      ...result,
      factId: row.id,
      userId: row.user_id,
      label: placeholderLabel(result.expansion),
    })
  }

  const work = flags.limit === null ? candidates : candidates.slice(0, flags.limit)

  /* ── 2. report, always, in both modes ───────────────────────────────────────────────────── */

  console.log(`nina_memory_facts — ${facts.length} row(s) read`)
  console.log(`\nPARSED — ${candidates.length} shortcut(s)${
    work.length === candidates.length ? '' : `, ${work.length} of them in this run (--limit)`
  }`)
  for (const c of candidates) {
    const mark = work.includes(c) ? ' ' : '·'
    console.log(
      `  ${mark} [${c.grammar}] ${c.trigger.padEnd(10)} ${c.kind.padEnd(5)} ` +
        `key=${JSON.stringify(c.matchKey).padEnd(12)} ${clip(c.expansion, 64)}`,
    )
  }
  console.log(
    `\n  label is the first ${LABEL_TARGET_CHARS} characters of the expansion, cut at a word` +
      '\n  boundary. It is a PLACEHOLDER for the operator to rewrite on /admin/shortcuts.' +
      '\n  This script never invents a description of the scene.',
  )

  console.log(`\nSKIPPED — ${skipped.length} row(s), left in the ledger untouched`)
  for (const s of skipped) {
    console.log(`  -   ${clip(s.text, 72)}`)
    console.log(`      ${s.reason}`)
  }

  /* ── 3. write, or explain that nothing was written ──────────────────────────────────────── */

  if (!flags.apply) {
    console.log(
      `\nnothing was written. ${work.length} shortcut(s) pending. Re-run with --apply.` +
        '\n(--apply --prune would then delete the ledger rows it wrote, by id.)',
    )
    process.exit(0)
  }

  console.log(`\nINSERT — ${work.length} row(s) into nina_shortcuts`)
  let inserted = 0
  for (const c of work) {
    const rows = await sql`
      insert into nina_shortcuts
        (id, user_id, "trigger", match_key, kind, label, expansion, enabled, created_at, updated_at)
      values
        (${newId()}, ${c.userId}, ${c.trigger}, ${c.matchKey}, ${c.kind},
         ${c.label}, ${c.expansion}, true, now(), now())
      on conflict (user_id, match_key) do nothing
      returning id
    `
    if (rows.length === 1) {
      inserted++
      console.log(`  +   ${c.trigger.padEnd(10)} ${rows[0].id}`)
    } else {
      console.log(`  =   ${c.trigger.padEnd(10)} already present, left exactly as it is`)
    }
  }
  console.log(
    `\ninserted ${inserted}, already present ${work.length - inserted}. The ledger is untouched.`,
  )

  if (!flags.prune) {
    console.log('Re-run with --apply --prune to clear the ledger rows these came from.')
    process.exit(0)
  }

  /* ── 4. prune: by id, and only against a byte-identical stored expansion ────────────────── */

  console.log('\nPRUNE — deleting the ledger rows whose shortcut is confirmed in nina_shortcuts')
  let deleted = 0
  let kept = 0
  for (const c of work) {
    const [stored] = await sql`
      select id, expansion
        from nina_shortcuts
       where user_id = ${c.userId}
         and match_key = ${c.matchKey}
       limit 1
    `
    if (!stored) {
      kept++
      console.log(`  !   ${c.trigger.padEnd(10)} not in nina_shortcuts — ledger row ${c.factId} kept`)
      continue
    }
    if (stored.expansion !== c.expansion) {
      kept++
      console.log(
        `  ~   ${c.trigger.padEnd(10)} a DIFFERENT expansion is stored — ledger row ${c.factId} kept.` +
          '\n      Someone edited it on /admin/shortcuts; this is the last copy of the original.',
      )
      continue
    }
    const gone = await sql`
      delete from nina_memory_facts
       where id = ${c.factId}
         and user_id = ${c.userId}
      returning id
    `
    if (gone.length === 1) {
      deleted++
      console.log(`  -   ${c.trigger.padEnd(10)} ledger row ${c.factId} deleted`)
    } else {
      kept++
      console.log(`  !   ${c.trigger.padEnd(10)} ledger row ${c.factId} was already gone`)
    }
  }
  console.log(
    `\ndeleted ${deleted} ledger row(s), kept ${kept}.` +
      '\nRe-run with no flag to confirm what is left.',
  )
  process.exit(0)
}
```

- **`--apply` HAS NOT BEEN RUN, BY ANYONE, AT ANY POINT.** Not by the implementing session, not by
  a verifier, not by CI, not "just to check the insert works". It writes production, and whether
  and when the ledger is migrated is the user's call — the whole reason the script defaults to a
  dry run. A session that runs `--apply` has failed this phase's exit criteria even if the import
  succeeds.
- `--prune` likewise. It deletes production rows.

## Handoffs

- **Rewriting the placeholder labels** is Phase 3's surface and the operator's job. The importer
  writes a 60-character slice of the expansion and says so; `/admin/shortcuts` is where that
  becomes a name for the scene. Nothing in this phase should try to be clever about it.
- **Actually running the import against production** is left to the user, after all four phases
  land. Suggested order, for whoever writes the set's closing note: dry run → read it → `--apply`
  → check `/admin/shortcuts` → `--apply --prune`.
- **The `MEMORY_FACT_LIMIT = 60` window and the `category: 'person'` mislabelling** of the rows
  that stay in the ledger (`lib/nina/load.ts:99`) are pre-existing and out of this plan set's
  scope entirely. Not touched, not fixed, noted here so nobody thinks it was missed.
- **A `--rollback` that puts pruned rows back** is deliberately not built. The rows are recoverable
  from `nina_shortcuts` if it ever matters, and an untested restore path on a production table is
  worse than not having one.
- **R1 and R2 are not served here.** If a step of this phase looked like it was serving the admin
  surface or the turn path, it has been removed.

## Rollback

`git revert` this phase's single commit. It deletes two new files and one `package.json` line.
Nothing else in the tree references any of it: no `lib/`, `app/` or `components/` module imports
the script, and no other test imports its helpers.

**If `--apply` was run despite the exit criteria:** the inserted rows are removable per-user with

```sql
delete from nina_shortcuts where user_id = '<id>';
```

**If `--prune` was run:** the deleted `nina_memory_facts` rows are gone from that table, but their
text survives verbatim as `nina_shortcuts.expansion` — the prune only fires on a byte-identical
match. Reconstructing a ledger row means re-inserting `nina_memory_facts` with
`category = 'person'`, `source = 'admin'`, `source_message_id = NULL` and the expansion wrapped
back into its original grammar. The original `id` and `created_at` are not recoverable. This is the
reason the exit criteria are worded the way they are.
