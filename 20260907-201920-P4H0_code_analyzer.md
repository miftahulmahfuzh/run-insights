## Detailed Requirements Understanding

**Problem/Requirement Statement**

Two collections of photographs exist, in two tables, and they are not the same thing:

| The runner calls it | Table | Admin route | What a row is |
|---|---|---|---|
| Nina Album | `nina_avatars` | `/admin/nina` | her profile album — has `folder`, thumbnails, `is_current` |
| Chat photos | `nina_message_images` | `/admin/photos` | a photograph inside the conversation |

Three defects, all in `nina_message_images`:

1. **The collection is a child of the conversation, so deleting a conversation destroys it.**
   `nina_message_images.message_id` is `NOT NULL REFERENCES nina_messages(id) ON DELETE CASCADE`,
   and `nina_messages.session_id` is `NOT NULL REFERENCES nina_chat_sessions(id) ON DELETE CASCADE`.
   One `DELETE` on a session chains through both. The photograph rows go; only the Blob bytes
   survive, unreferenced (`lib/nina/queries.ts:868` `removeNinaSession`, and the schema's own comment
   at `lib/db/schema.ts:906-910` states this as a *requirement*, R11 of the sessions feature).
   A photograph the operator replaced by hand is destroyed by exactly the same statement, because
   `replaceChatPhotoAction` deliberately keeps the row and its `message_id`
   (`lib/nina/queries.ts:1692` `updateNinaChatPhotoBlob`).

2. **An album photograph can become a Chat photos row.** `resolveAttachment`'s avatar branch
   (`lib/nina/actions.ts:192-215`) reads a `nina_avatars` row and copies its `blob_url` and
   `pathname` onto a **new** `nina_message_images` row with `kind: 'generated'`
   (`lib/nina/actions.ts:564-575`). `/admin/photos` lists exactly `kind = 'generated'`
   (`generatedChatPhotoScope`, `lib/nina/queries.ts:1577`), so her album photograph now appears in
   the Chat photos collection as well — the carry-over the user reports.

3. **A Chat photos row can be duplicated.** The same function's image branch
   (`lib/nina/actions.ts:218-231`) copies `blob_url`/`pathname` from another `nina_message_images`
   row onto a new one. Two collection rows, one photograph.

**Success Criteria**

- Deleting a chat session leaves every `nina_message_images` row in place. The rows survive with no
  message; `/admin/photos` still lists them; the conversation they belonged to is gone.
- Deleting a single **message** still takes its photographs (unchanged behaviour — see Decisions in
  the plan index).
- `/admin/photos` lists each photograph at most once, and lists no photograph that is a
  `nina_avatars` row.
- Attaching an **orphaned** chat photograph to a message adopts it: the same row's `message_id`
  becomes that message's id, so the photograph is back in a conversation and is still the same row,
  the same id, the same `created_at` and the same Blob object. No second row is written, so the
  adoption cannot produce the duplicate R3 forbids.
- Attaching a chat photograph that **still has** a message leaves that message's bubble intact —
  adoption never steals a photograph out of a live bubble.
- Existing production rows that already violate R2/R3 are brought into line **without deleting a
  row or a Blob object**.
- `npm run typecheck`, `npm run lint`, `npm test` green at the end of every phase.

**Key Considerations**

- *"don't delete existing photos"* is the overriding value in this request and it constrains the fix
  itself: no phase may delete a row or a Blob object to satisfy R2/R3.
- `message_id` is currently `NOT NULL` and the column's own comment argues for it — *"an image with
  no message is nothing"* (`lib/db/schema.ts:1039`). R1 overturns that sentence. The comment must be
  rewritten, not merely contradicted.
- Blob objects are **shared** between rows and between tables today, which is why
  `isBlobPathnameReferenced` (`lib/nina/queries.ts:1791`) exists. Nothing in this work may make an
  unconditional `del()` reachable.
- A row with no message cannot be deep-linked into the conversation. `galleryPhotos` carries
  `messageId` for that purpose (`lib/nina/album.ts:304`) and `attachableIdAt`
  (`lib/nina/chatphotos.ts`) hands the image id to the re-attach path.
- Assumption: `/admin/photos` — `listNinaChatPhotos` — **is** what the user means by "Chat photos
  collection". It is the only surface in the repo that carries that name
  (`CHAT_PHOTO_COLLECTION_LABEL`, `components/admin/ChatPhotoGrid.tsx`).
- Assumption: the user does not want the album→chat share feature or the re-attach feature removed.
  Neither was mentioned, both shipped deliberately (F33 R26, F34 R2), and the plan therefore keeps
  them working while excluding their rows from the collection.

## Current Dataflow

### Entry Point: `deleteNinaSessionAction`

**Location:** `lib/nina/sessionActions.ts:228`
**Trigger:** the sidebar's delete control in `/nina`
**Input Schema:** `{ sessionId: string }`
**Validation:** zod shape, then owner scope inside the query
**Next Step:** `removeNinaSession(userId, sessionId)` — `lib/nina/queries.ts:868`

### The destructive path (R1)

`removeNinaSession` is a four-statement `db.batch`. Statements 1–3 purge the distilled memory
ledger (R8 of the sessions set). Statement 4 is:

```
DELETE FROM nina_chat_sessions WHERE user_id = $1 AND id = $2
```

Postgres then chains, and **both hops are declared cascades**:

```
nina_chat_sessions.id
  └─ nina_messages.session_id      NOT NULL, ON DELETE CASCADE   (lib/db/schema.ts:925-928)
       └─ nina_message_images.message_id  NOT NULL, ON DELETE CASCADE  (lib/db/schema.ts:1039-1042)
```

So one session delete destroys every photograph row in that conversation:

- `finishSelfie`'s generated selfies (`lib/nina/imagerun.ts:203`) — the *"painstakingly generated by
  llm"* photographs;
- every photograph added by hand through `addChatPhotoAction` (`lib/admin/chatPhotoActions.ts:206`);
- every photograph **replaced** by hand, because `updateNinaChatPhotoBlob` keeps the row on its
  original message by design (`lib/nina/queries.ts:1692`, *"the bubble that already exists keeps
  existing and now shows the new picture"*). This is the user's second report, and the reason it is
  the same bug: a replaced photograph is not a new row, it is old bytes swapped under an old row.

The Blob objects are **not** deleted (`removeNinaSession`'s header states this deliberately), so the
bytes of every lost photograph are still in the store as orphans — which is what makes R1
recoverable in principle and is the reason `scripts/blob-reap.mjs` must not be run before this
lands.

### The carry-over path (R2)

```
/admin/nina  ─ ninaPhotoShareUrl(origin, avatarId)          lib/admin/shareToNina.ts:36
             → /nina?photo=avatar:<id>                       PHOTO_PARAM, lib/nina/attach.ts:126
             → parseNinaPhotoParam                           lib/nina/attach.ts:154
             → sendNinaMessage({ attachExisting })            lib/nina/actions.ts:329
             → resolveAttachment  ── avatar branch            lib/nina/actions.ts:192
                 getNinaAvatar(userId, id)                    → { blobUrl, pathname, kind:'generated', description }
             → insertNinaMessageImages(...)                   lib/nina/actions.ts:564
```

**No bytes are copied** — this is the stated optimisation of F34 R2 (*"we dont actually reupload the
photo into the chat, but just some kind of pointer to the existing file"*). The consequence is the
defect: the new row's `pathname` is `nina/<userId>/avatar-<id>.jpg`, an **album** object, and
`kind` is forced to `'generated'` (`lib/nina/actions.ts:207-215`, *"the gallery's his/hers
discriminator has to keep telling the truth about a photo that has now appeared twice"*). Since
`/admin/photos` selects on `kind = 'generated'` alone, the album photograph is now a Chat photos
row.

### The duplication path (R3)

The same function, image branch (`lib/nina/actions.ts:218-231`): `getNinaMessageImage` →
`{ blobUrl, pathname, kind: row.kind, description }` → a second `nina_message_images` row with the
same `pathname`. If the origin row was hers, both rows are `kind = 'generated'` and the collection
shows the same photograph twice. Reachable from the chat's own photo viewer via `attachableIdAt`
(`lib/nina/chatphotos.ts`), so it is a runner-facing loop and not an admin-only one.

### The same entry point is what R4 asks to be re-pointed

R4 is not a new surface. It is the **image branch above, redirected**: today it reads a row and
inserts a copy of it; R4 says that when that row has no message, the row itself is to be moved onto
the new message. The whole path already carries what an adoption needs and nothing has to be added
to reach it:

```
chat photo viewer ─ attachableIdAt(ids, index)          lib/nina/chatphotos.ts  → nina_message_images.id
  or /admin/photos ─ ninaPhotoShareUrl-shaped link       (image pointer, not avatar)
  → /nina?photo=image:<id>                               PHOTO_PARAM
  → parseNinaPhotoParam → { kind:'image', id }           lib/nina/attach.ts:154
  → sendNinaMessage({ attachExisting })                  lib/nina/actions.ts:329
  → resolveAttachment ── image branch                    lib/nina/actions.ts:218
      getNinaMessageImage(userId, id)                    ← owner-scoped, already proves the row is his
  → insertNinaMessageImages(...)                         lib/nina/actions.ts:564   ← THE COPY
```

Two facts from the read above decide the shape of the fix rather than leaving it to taste:

- **`getNinaMessageImage` is already owner-scoped**, so `resolveAttachment` has, at that line, a row
  it has proved belongs to the caller. An adoption is therefore an `UPDATE … WHERE user_id = $1 AND
  id = $2 AND message_id IS NULL` and needs no new authorization argument.
- **The runner message is inserted before the image block runs** (`lib/nina/actions.ts:504-517`,
  then `:527-576`), so the message id an adoption has to write is already in hand — `runnerMessageId`
  — and the ordering the file's header calls part of its contract is unchanged.

`message_id IS NULL` in the WHERE is what makes "adopt an orphan" and "leave a live bubble alone"
one statement instead of a branch on a value read a moment earlier: a row that gained a message
between the read and the update is not adopted, and the caller falls back to the reference row.

**`sort_order` and `created_at`:** an adoption sets `sort_order` to its position in the new message
and must NOT touch `created_at` — `updateNinaChatPhotoBlob`'s recorded reason applies unchanged
(`lib/nina/queries.ts:1692`, *"the gallery is ordered by it … replacing a photograph is not taking a
new one"*). Adopting one is not taking a new one either, and a bumped `created_at` would silently
re-sort `/nina/about` and `/admin/photos`.
