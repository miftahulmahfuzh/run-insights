## Detailed Requirements Understanding

### R1 — one table, zero confirmations

**Problem statement.** `/admin/memory` today is two visually distinct sections built from two
different tables with two different write models, and every destructive path is gated behind a
second step:

- **Slots** (`nina_memory_slots`) — nine closed-vocabulary keys, rendered as nine `Card`s in a
  two-column grid, each a `<textarea>` plus Save / Retire. `Retire` opens an inline panel with an
  optional "Why" field and a second **Record and retire** button.
- **Ledger** (`nina_memory_facts`) — an append-only list rendered as one `Card` per row, each with
  three buttons: **Retract** (opens a panel with an optional replacement textarea and a second
  button), **Edit** (only on rows whose `source = 'admin'`; opens an inline three-field grid with
  Save/Cancel), and **Purge** (opens a red panel demanding the literal string `PURGE` be typed).
- **Pending promises** (`pending_promises`, a structured slot) — a third render shape, a `<ul>` of
  panels with a Remove button each.

So "all the memory" is three shapes across two tables, and there are four separate two-step
confirmation flows (retire, retract, purge, and the `PURGE` string gate inside purge).

**What must change.**

1. **One table.** Slots, ledger rows and pending promises all become rows in a single tabular
   surface. The `kind` of a row stays visible (it decides what an edit means at the storage layer)
   but stops deciding what the row *looks like*.
2. **Edit in place, on every editable row, with no mode switch and no second button.** Today an
   edit costs: click Edit → panel opens → change field → click Save. The target is: change the
   cell → it saves.
3. **One destructive control per row, which deletes.** No `PURGE` string, no red panel, no
   "record it first" step. `retractFactAction` and `retireSlotAction` — whose entire purpose is to
   append a quoting record *before* deleting — are the confirmation-shaped mechanism the user is
   asking to stop paying for.
4. **Add a row from the same table.** Today "add" exists only for facts, as a separate `Card`
   above the list (`InsertFact`), and does not exist at all for slots (`saveSlotAction` doubles as
   an upsert, and the page pre-renders an empty card per key so nothing has to be "added").

**Success criteria.** One `<table>` on `/admin/memory`. Every row is editable inline where the
storage layer permits it. Delete is one click and the row is gone. Add is one row-shaped affordance
in the same table. No component in `components/admin/` retains a `mode`/`confirming` state whose
only job is to interpose a second click on a destructive action.

**Key considerations and constraints.**

- **`canEditInPlace` is a storage fact, not a safety rail** — and this is the one distinction that
  survives the confirmation purge. `factPermissions` (`lib/admin/memoryModel.ts:135`) refuses an
  in-place edit of a **distilled** row because that row carries a `source_message_id` pointing at a
  real chat message, and rewriting its text makes it misquote that message. That is a *data
  integrity* reason, not a "are you sure" reason. The honest resolution, and the one this plan
  takes: editing such a row is allowed but **re-labels it** `source = 'admin'` and clears
  `source_message_id`, because a sentence the admin wrote is no longer a quotation of a message.
  It is one write, no prompt, and the pointer stops being a lie.
- **The slot vocabulary is closed** (`lib/admin/memoryVocab.ts`, nine keys) and
  `canonicaliseSlotValue` refuses values that do not parse for typed keys. A refusal is not a
  confirmation — it is a validation failure and must still be reported, inline on the row.
- **`pending_promises` cannot be edited as free text.** `canonicaliseSlotValue` returns `null` for
  it on purpose ("a string is never a promise") because `lib/nina/promises.ts` evaluates `metric`,
  `target` and `byDate` against precomputed facts. Its entries stay per-row deletable and
  read-only-as-text.
- **Nothing here is cached.** `loadNinaContext` reads both tables live on every turn, so a
  committed row reaches Nina's next prompt with no invalidation step. `revalidatePath` only
  re-renders the admin page.

### R2 — Nina's chat photographs, in `/admin`

**Problem statement.** There are **two** separate photo stores in this application and the admin
page shows exactly one of them.

| | `nina_avatars` | `nina_message_images` |
|---|---|---|
| What it holds | her profile-picture album | every photo in the conversation, his and hers |
| Whose | hers only | `kind = 'upload'` is his, `kind = 'generated'` is hers |
| Foldered | **yes** — `folder text NOT NULL DEFAULT ''`, plus a `nina_folders` table | **no** — no folder column exists |
| Shown in `/admin` | yes, `/admin/nina`, as a full file manager | **no** |
| Shown to the runner | `/nina/about` album strip | `/nina/about` gallery strip, and inline in chat |
| Written by | the worker's `finishAvatar`, admin upload, the seed | the worker's `finishSelfie` (`kind='generated'`), the chat send path (`kind='upload'`), the attach path |

R2 is about the **second** table, restricted to `kind = 'generated'` — *"nina generated images"*.
Those rows are written by `scripts/nina-image-worker.ts:433-448` as a pair: a `nina_messages` row
(`role='nina'`, `source='chat'`, a caption, `turn_id = jobId`) and a `nina_message_images` row
(`kind='generated'`, `prompt` = the generation sidecar, `description` = the scene prose).

**What must change.**

1. A surface in `/admin` that lists every `kind='generated'` row for the user, newest first,
   paginated. *"Put them into a folder or something"* — the folder is the presentation, and the
   honest one here is a single named collection rather than a nested tree, because unlike
   `nina_avatars` these rows have **no folder column** and inventing one would mean a migration
   and a second folder grammar for a set the user described as one bucket.
2. **Replace** — swap the bytes behind an existing row, keeping the row, its message, its position
   in the conversation, and its `created_at`. The chat bubble that already exists keeps existing
   and shows the new picture.
3. **Add** — *"so it is like nina generated them, but actually it is manually added by user"*. This
   is a literal specification of the storage shape: the added photo must be indistinguishable, to
   every reader, from one `finishSelfie` wrote. Since `message_id` is `NOT NULL`, adding a photo
   **necessarily mints a `nina_messages` row too** — exactly the pair the worker writes.
4. **Remove** — delete the row, and the blob behind it.

**Success criteria.** `/admin` has a route listing her chat photographs. Each supports replace,
remove; the collection supports add. A photo added there appears in the runner's chat and in
`/nina/about`'s gallery, on her side, with no marker distinguishing it from a generated one.

**Key considerations and constraints.**

- **`message_id` is `NOT NULL` with `ON DELETE CASCADE`** (`lib/db/schema.ts:950-952`), and the
  column's own comment states the intent: *"an image with no message is nothing."* So there is no
  such thing as a floating chat photo, and "add a photo" is unavoidably "add a message with a
  photo on it". The plan does exactly what the worker does and does not invent a third shape.
- **The reverse question — what happens to the message when the last photo is removed — has to be
  answered.** The worker's caption message exists only to carry the photograph; leaving it behind
  produces a bubble with a caption and no picture, in the runner's chat, forever. See "Open
  design decisions" below; the plan resolves it.
- **`insertNinaMessageImages` validates the message FK by hand** against the caller's own messages
  (`lib/nina/queries.ts:1206-1213`) and returns `[]` rather than throwing if it does not match.
  Any new write path must not silently swallow that `[]` as success.
- **Blob lifecycle.** `lib/admin/ninaAlbumActions.ts` already imports `del` from `@vercel/blob` and
  is the established pattern for removing an object when its row goes. A **replace** creates a new
  object and orphans the old one — the `reap-orphaned-blobs` skill exists precisely because
  orphans accumulate, so the replace path must delete the old object rather than rely on the reaper.
- **The upload handshake exists and is admin-gated.** `app/api/admin/nina/upload/route.ts` mints a
  short-lived client-upload token, and refuses any pathname that is not
  `isAdminAvatarRequestPathname` / `isAdminAvatarThumbRequestPathname`. A chat photo's pathname is
  `nina/<userId>/chat/<id>.jpg` (`ninaChatPathname`, `lib/nina/images.ts:85`) and is **not**
  accepted by that route today. The route's own docstring records that its four parameters were the
  reason it is a separate route from `/api/upload` — the same argument applies to adding a third
  accepted pathname shape here rather than a fourth route.
- **Invariant 5** (`lib/nina/chatphotos.ts:14-19`): the image row's `description` is `glm-4.6v`'s
  private prose and its only consumer is Nina's prompt. An admin surface may show it — `/admin` is
  where the operator reads exactly this — but nothing it renders may leak into a runner-facing
  caption.

## Current Dataflow

### R1 — `/admin/memory`

#### Entry point: `AdminMemoryPage`

**Location:** `app/admin/memory/page.tsx:38`
**Trigger:** GET `/admin/memory?user=<id>`; `export const dynamic = 'force-dynamic'`
**Validation:** `requireAdmin()` first statement; `?user` falls back to the signed-in admin's id;
`getAdminUser` returning `null` renders the "no such user" branch.

**Reads, all `Promise.all`'d:**

| Call | File:line | Returns |
|---|---|---|
| `listAdminUsers()` | `lib/admin/users.ts` | the picker's options |
| `getAdminUser(targetId)` | `lib/admin/users.ts` | `{ id, email, slots, facts }` |
| `adminReadSlots(target.id)` | `lib/admin/memoryStore.ts:120` | `NinaSlotRow[]` |
| `adminReadFacts(target.id, 200)` | `lib/admin/memoryStore.ts:130` | `NinaFactRow[]`, newest first |
| `adminReadSlot(target.id, 'pending_promises')` | `lib/admin/memoryStore.ts:125` | one parsed slot |

**Transform:** `buildSlotCards(slotRows)` → `SlotCard[]` (the closed vocabulary joined onto what
exists, so an unset key still yields a card); the promises slot's `value` is narrowed to
`NinaPendingPromisesSlot` and its `promises` array taken; `factRows.map(...)` → `FactCard[]`,
stamping `canEditInPlace` / `editNote` from `factPermissions(row)` and rendering `createdAt` to an
ISO string.

**Exit:** `<MemorySlots userId slots promises />` and `<MemoryLedger userId facts hiddenCount total />`.
Both are `'use client'` and receive only plain serializable props — deliberate, so neither zod nor
the drizzle schema is bundled for the browser.

#### Write chain: nine Server Actions

Every one of them is `lib/admin/memoryActions.ts` and follows the same four steps in the same
order: `await requireAdmin()` → Zod → write through `memoryStore` → `revalidatePath('/admin/memory')`.

| Action | Line | What it writes | Confirmation shape today |
|---|---|---|---|
| `saveSlotAction` | 88 | upsert slot, `source='admin'` | none |
| `recordSlotAsFactAction` | 124 | append fact | none (a fallback button) |
| `retireSlotAction` | 166 | **append** a retirement fact, **then** delete the slot | inline panel + second button |
| `removePendingPromiseAction` | 231 | rewrite the promises slot minus one entry | none |
| `insertFactAction` | 289 | append fact, `source='admin'`, null message id | none |
| `editFactAction` | 321 | update a fact in place | inline panel + Save |
| `retractFactAction` | 369 | **append** a quoting fact, **then** delete the original | inline panel + second button |
| `purgeFactAction` | 432 | delete a fact, nothing else | red panel + type `PURGE` |

**State changes.** `nina_memory_slots` is upserted on `(user_id, key)`; `nina_memory_facts` is
append-only from the distiller's side and directly mutable only from here. `memoryStore` is the
only module that stamps `source: 'admin'` — `memoryActions` never writes a row itself, which is
the stated reason the store exists.

**The ordering rule, and why it is about to become moot.** `memoryActions.ts:52-58` records that
`retractFactAction` and `retireSlotAction` each perform two statements outside a transaction and
that **the append comes first, always**, so a crash leaves a recoverable duplicate rather than a
hole. R1 deletes the append half of both, which deletes the rule along with it — this analysis
records it so the plan is deliberate about removing an invariant rather than tripping over it.

#### Exit points

`revalidatePath('/admin/memory')` re-renders this page. It is **not** how the edit reaches Nina:
`loadNinaContext` (`lib/nina/context.ts`) reads `nina_memory_slots` and the newest 60
`nina_memory_facts` live on every turn, with no cache on that path.

### R2 — Nina's generated chat photographs

#### Entry point A (the writer): `finishSelfie`

**Location:** `scripts/nina-image-worker.ts:427`
**Trigger:** the GitHub Actions worker, after a successful generation
**Statements, in this order and load-bearing per its docstring:**

1. `insert into nina_messages (id, user_id, role, text, source, turn_id, reply_to_id) values (…, 'nina', ninaImageCaption(jobId), 'chat', jobId, (subselect))`
2. `insert into nina_message_images (id, user_id, message_id, kind, blob_url, pathname, width, height, bytes, description, prompt, sort_order) values (…, 'generated', …, args.scene, args.sidecar, 0)`
3. `update nina_turns set status='ok' …`

**The pair, not the row, is the unit.** The docstring is explicit that this is *"not a special kind
of message"* — an ordinary `nina_messages` row plus an image row — and that this is what makes the
photograph quotable, gallery-able and unread-able "for free". Any admin-side "add a photo" that
writes only an image row would have to invent a message to hang it on anyway (`message_id` is
`NOT NULL`); writing the same pair is the only shape that reads identically downstream.

#### Entry point B (the other writer): `sendNinaMessage`

**Location:** `lib/nina/actions.ts`, two blocks
- `:490` — `kind: 'upload'`, one row per picked file, `sortOrder: index`. His photographs.
- `:520` — the R26 attach path: `kind: attached.kind`, which is `'generated'` when he re-attaches
  one of her selfies from the album (`:167-172`). This is why `photoSideOf` reads `kind` and not
  `message.role`: a `role='runner'` message can carry a `kind='generated'` photograph.

**Consequence for R2, and it is a real one.** "All the Nina-generated images in the chat
collection" is `kind = 'generated'`, and that set includes rows hanging off **runner** messages —
the re-attached ones. They are hers by `kind`, and the admin surface must not filter by
`message.role` or it will miss them and disagree with `/nina/about`'s gallery.

**And a second consequence, which is a data-loss hazard rather than a listing bug.**
`resolveAttachment` (`lib/nina/actions.ts:143-192`) **copies `blobUrl` and `pathname` off an
existing row onto the new one. No bytes are copied** — that is the stated design, *"a pointer to
the existing file"*, R26's whole point. Both of its branches do it:

- `attach.kind === 'avatar'` → `getNinaAvatar(userId, attach.id)`, returned with `kind: 'generated'`.
  The new chat row's blob object is **shared with a `nina_avatars` row** — possibly the one that is
  her current profile picture.
- otherwise → `getNinaMessageImage(userId, attach.id)`, returned with `kind: row.kind`. Shared with
  **another `nina_message_images` row**.

So **one Blob object can be referenced by several rows across two tables**, and a delete path that
calls `del(pathname)` whenever it removes a row can blank an earlier chat bubble or break her
profile picture while both rows still point at the dead URL. Invariant 8 ("no orphaned blobs") and
this fact pull in opposite directions, and correctness wins: an orphan costs storage, a
deleted-but-referenced object is visible data loss. Any remove or replace must check both tables
for a surviving reference before deleting the object.

#### Read chain

| Reader | File:line | Query | Index |
|---|---|---|---|
| `/nina/about` gallery | `app/nina/about/page.tsx:33` | `listNinaMessageImages(userId, { limit: NINA_GALLERY_LIMIT })` | `nina_message_images_user_created_idx` |
| chat message hydration | `lib/nina/queries.ts:1287` | `getNinaMessageImagesForMessages` | `nina_message_images_message_idx` |
| one photo by id | `lib/nina/queries.ts:1266` | `getNinaMessageImage`, `(user_id, id)` | PK |
| Nina's own context window | `lib/nina/context.ts` | via the message window join | message idx |

`imageColumns` (`lib/nina/queries.ts:469-481`) is the shared projection: `id, messageId, kind,
blobUrl, pathname, width, height, bytes, description, prompt, sortOrder, createdAt`. **There is no
`count` query and no `offset` reader** for this table — every existing read is either "the newest
N" or "these message ids". A paginated admin listing has no query to reuse.

#### Data persistence

**Blob — and the two pathname shapes are NOT the same.** This was stated wrongly in the first
draft of this document and is corrected here, verified against the code:

| Whose | Written by | Pathname | Type |
|---|---|---|---|
| **his** uploads (`kind='upload'`) | the runner's composer, via `/api/upload` | `nina/<userId>/chat/<id>.jpg` — `ninaChatPathname` (`lib/nina/images.ts:85`), re-validated by `isNinaChatRequestPathname` (:104) | `image/jpeg` only, ≤ `NINA_CHAT_MAX_UPLOAD_BYTES` (900 000), because the composer always compresses to JPEG first |
| **hers** generated (`kind='generated'`) | `scripts/nina-image-worker.ts:375-392` (`store`) | `nina/<userId>/selfie-<id>.png` — `ninaImagePathname(userId, purpose, id)` (`lib/nina/imagerecipe.ts:126`) | `NINA_IMAGE_CONTENT_TYPE` = **PNG**, 768×1024, `addRandomSuffix: true`, `allowOverwrite: false` |

R2's set is the **second** row. `isNinaChatRequestPathname` requires four segments ending `.jpg`
and does not match a selfie pathname — so the upload route's third branch cannot reuse that
predicate, and the `NINA_CHAT_*` ceilings are the wrong constants to inherit for it.

`lib/nina/imagerecipe.ts` carries the **same zero-import rule** as `lib/nina/images.ts` — its
docstring states that importing `NINA_BLOB_PREFIX` would cost it *"the zero-import property the
Actions worker depends on"*, and `tests/nina.imagerecipe.test.ts` asserts the duplicated prefix
agrees instead. Read from it; add nothing to it.

**No thumbnails.** `nina_message_images` has no `thumb_url` column, unlike `nina_avatars`. The grid
in `/nina/about` renders the originals. At the sizes an admin grid draws, this is the same tradeoff
`components/nina/NinaPhotoGrid.tsx:56-58` already recorded (`next/image` on Blob-hosted photos costs
a paid transform quota), and it is a known cost rather than a thing to fix in this round.

#### Exit points

The photograph reaches the runner in three places, all from the same rows: inline in the chat
bubble, in `/nina/about`'s gallery strip, and — when tapped — in `PhotoViewer` via
`chatViewerPhotos`, whose accessible name comes from `NINA_SIDE_LABEL[photoSideOf(kind)]`.

## Key Data Structures

### `nina_memory_slots` — `lib/db/schema.ts:1077`
`(user_id, key)` primary key, `value jsonb`, `source` (`'distilled' | 'admin'`),
`source_message_id` nullable, `updated_at`. Nine keys in the closed vocabulary; `pending_promises`
is the one structured value.

### `nina_memory_facts` — `lib/db/schema.ts:1121`
`id` nanoid PK, `user_id`, `category`, `text`, `confidence`, `source`, `source_message_id`
nullable, `created_at`. Append-only from the distiller; `adminUpdateFact` / `adminDeleteFact` are
the only mutations.

### `SlotCard` / `FactCard` — `lib/admin/memoryModel.ts:79,104`
The serializable props crossing the RSC boundary. `FactCard` carries the precomputed
`canEditInPlace` + `editNote` so the client never imports the predicate's dependencies.

### `nina_message_images` — `lib/db/schema.ts:940`
```
id text PK | user_id text NOT NULL -> user(id) cascade
message_id text NOT NULL -> nina_messages(id) cascade     <-- no floating photos
kind text NOT NULL          'upload' (his) | 'generated' (hers)
blob_url text NOT NULL | pathname text NOT NULL
width/height/bytes integer NULL
description text NULL       glm-4.6v's private prose; invariant 5
prompt text NULL            the generation sidecar, kind='generated' only
sort_order integer NOT NULL DEFAULT 0
created_at timestamptz NOT NULL DEFAULT now()
```
Indexes: `nina_message_images_message_idx (message_id)`,
`nina_message_images_user_created_idx (user_id, created_at desc)`.

**There is no `(user_id, kind, created_at)` index.** A `kind='generated'`-filtered, paginated
listing reads `nina_message_images_user_created_idx` and filters `kind` as a residual predicate.
At this table's size (one user, a handful of generations a day, single-digit thousands of rows at
the horizon) that is a bounded index scan and correct as-is; the plan notes it rather than adding
an index nothing has measured a need for.

### `NinaImageRow` / `NinaImageInsert` — `lib/nina/queries.ts:176,191`
The row and insert shapes `imageColumns` projects into.

### `ExplorerPhoto` — `components/admin/explorer/model.ts`
`/admin/nina`'s grid prop. Carries `folder`, `filename`, `crop`, `isCurrent`, `source` — four
fields `nina_message_images` has no counterpart for, which is the concrete reason R2 gets its own
prop type rather than reusing this one.

- `blobEnv()` — `BLOB_READ_WRITE_TOKEN`, read by the upload route
- `AUTH_URL` via `shareOrigin()` — `server-only`, invariant 9 forbids a `NEXT_PUBLIC_` for it
- `requireAdmin()` — the only gate; `proxy.ts` matches neither `/admin` nor `/api/*`, verified at
  `lib/admin/requireAdmin.ts:13-16`

### External services
- **Vercel Blob** — `put` (client handshake), `del` (`lib/admin/ninaAlbumActions.ts:3`),
  `rename` (`lib/share/rotateBlobs.ts`, unrelated)
- **Neon Postgres** via drizzle
- **GitHub Actions** — `nina-image.yml`, the generation worker. Not on any path this round touches.

### Implicit
- Next.js **16.3.1**. `PageProps<'/admin/…'>` / `LayoutProps<'/admin'>` are globally available
  helpers and `searchParams` is a promise that must be awaited —
  `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/page.md`, "Page Props
  Helper". Both admin pages already use them; a new route must.
- `ci:client-secret-guard` — `scripts/check-client-secret-boundary.mjs`. Its Rule 3 exempts only
  lines a comment scanner recognises, which is why every JSX comment in `app/admin/nina/page.tsx`
  carries a leading `*` on continuation lines.
- The invariant checkers in `scripts/check-*.mjs` run in CI (`.github/workflows/ci.yml`).

   three prop bundles.

   described in "Key considerations".

   arrive.
