## Detailed Requirements Understanding

**Problem/Requirement Statement**: `lib/nina/queries.ts` is a 4573-line module holding every
Nina read/write against the `nina_*` tables, organized as 20 banner-delimited sections
(§1–§12 with sub-banners). It is the largest file in the repo. The work is a mechanical,
behavior-preserving redistribution of those sections into ~13 domain modules under
`lib/nina/queries/`, with `lib/nina/queries.ts` retained as the public barrel so no importer
changes. The layer-wide contract prose stays on the barrel; each section's own prose travels
with its code.

**Success Criteria**:
- `lib/nina/queries.ts` ends as a short file: layer-invariant header + one re-export per domain module.
- Every one of today's public exports resolves from `@/lib/nina/queries` exactly as before (runtime value exports verified by a new snapshot contract test; type exports verified by `tsc` against the 14 live importers).
- The 4 column lists (private today) are shared between sibling modules WITHOUT becoming
  public API at all: they are exported from `queries/columns.ts` for sibling `import`, and the
  barrel imports them — it never re-exports them (frozen by the barrel contract test).
- Every § banner paragraph moves with its section, byte-identical, under a provenance header.
- All existing tests pass; `tsc --noEmit`, eslint, prettier and a real `next build` pass.
- No file under `.workflows/plan/**` or `docs/plans/archive/**` changes.

**Key Considerations**:
- `verbatimModuleSyntax: true` + `isolatedModules: true` — `export * from` is immune to both;
  explicit `export { X } from` of a type would need `export type`. The barrel uses `export *`.
- `export * from './queries/x'` brings names into the barrel's EXPORT surface but NOT its local
  scope. Remaining in-queries.ts code that calls a moved symbol needs an explicit
  `import { … } from './queries/x'`. `tsc` catches every miss.
- A moved module must import foundations and already-moved siblings only — never the barrel —
  or the final state is a circular re-export chain. The measured code-level DAG (below) is
  acyclic, and the phase order topologically sorts it.
- Private helpers that cross module boundaries after the split become exports of their owning
  module, marked "internal — shared with sibling query modules". The two §5 helpers
  (`isOriginalPhoto`, `generatedChatPhotoScope`) DO join the public surface via the barrel's
  `export *` — accepted and documented (Decision 3; the frozen list grows 83 → 85 in phase 4).
  The 4 column lists do NOT: the barrel imports `./queries/columns`, never re-exports it, so
  they stay module-internal.
- This worktree's `node_modules` is a symlink to the main checkout's — vitest/tsc pass through
  it, Turbopack (`next build`) rejects it. Phase 1 replaces it with a real install and runs a
  build smoke so the set's riskiest unknown (new-directory resolution under Turbopack) is
  retired in the first phase, not the last.
- `npm run typecheck` = `next typegen && tsc --noEmit`; typegen is required for PageProps types.
- The memory note "a node_modules SYMLINK passes vitest+tsc but Turbopack's build rejects it"
  is the source of constraint R10's install step.

`lib/db/schema.ts` tables; no behavior. The four column lists (§2) are drizzle column
