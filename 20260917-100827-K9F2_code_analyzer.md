## Detailed Requirements Understanding

**Problem/Requirement Statement:** In the observed production turn, the runner referred to an existing photograph already visible in the conversation ("foto ini" — this photo) and asked Nina to use it as her profile picture. Instead, Nina's chat turn invoked the ONLY avatar-changing tool that exists (`set_avatar`), which by construction always launches a brand-new image-generation job from a text `scene` description. The model, forced through this one tool, fabricated a `scene` that echoed the recent conversation ("ripped jeans... alleyway...") rather than reusing the actual photo referenced. The result LOOKED like the right feature (a new profile picture landed) but was the wrong ONE (Case B's behavior, triggered by Case A's words), because there is no code path in the chat pipeline for "make an already-existing photograph her avatar, unchanged."

**Success Criteria:**
- A chat tool exists that adopts a specific existing photo (an attachment on the runner's current message, or the most recently shown photo in the conversation) as Nina's current avatar, copying its bytes with **no** image-generation job.
- The existing `set_avatar` tool (new-generation path) and `generate_image` tool (chat-only new photo) are undisturbed in behavior, but their descriptions are adjusted just enough that the model reliably distinguishes "use this one" from "make me a new one."
- R1 and R3 need **no new code** — both are already fully implemented (see Dataflow below); the plan's only job is R2, plus the minimal tool-description edits that let the model choose between all three correctly.

**Key Considerations / Edge Cases:**
- The model never sees a photo's row id — `lib/nina/context.ts`'s `imageDescriptions` gives it prose only. A new tool therefore **cannot** take a photo-id argument; the *handler* must resolve "this photo" deterministically from structural facts (what's attached to the current message; failing that, the most recent photo shown in this conversation), not from a model-supplied id.
- A referenced photo that is itself a **re-share** of another photo/avatar (`source_avatar_id`/`source_image_id` set) must be refused rather than copied twice — this is the same rule `lib/admin/ninaAlbumAvatarActions.ts`'s `setChatPhotoAsAvatarAction` already enforces for the admin path, and the new chat tool must enforce identically.
- The adoption is **synchronous** (a blob copy, not a 1-2 minute generation job), so — unlike `set_avatar`, which must not let her claim the change happened yet — this tool's answer should let her announce the change **in the same reply**, and the row must be marked announced at that moment so the proactive `avatar_changed` cron does not announce it a second time later.
- `NinaAvatarSource` already has an `'operator'` member that is defined but **never used anywhere in the codebase** (`lib/db/schema/nina/avatars.ts:16`) — a ready-made, semantically correct value for "a person, not the generator, chose this exact photo," to be used for the newly-adopted rows.
- The admin adoption path (`setChatPhotoAsAvatarAction`) is a separate, working, tested feature that must not be touched or regressed; the new chat-facing capability is additive.

## Current Dataflow

### Entry Point: a chat turn

**Location:** `lib/nina/actions/send.ts:sendNinaMessage` → `lib/nina/actions/startTurn.ts` (`after(() => runNinaBackgroundTurn(input))`) → `lib/nina/turnrun.ts:runNinaBackgroundTurn`
**Trigger:** the composer's Server Action call, `ChatScreen.handleSend`.
**Input:** `{ body, imageTickets?, replyToMessageId?, runId?, attachExisting?, dedupedImageIds?, contentHashes?, sessionId }`.

`resolveAttachment` (`lib/nina/actions/send.ts:188-256`) is what turns an `attachExisting: { kind: 'avatar' | 'image', id }` pointer (the Media picker's "attach this") — or a fresh `imageTickets` upload — into a **`nina_message_images` row parented to the runner's new message**, written **before** the background turn starts. This is the row a new "use this photo" tool must be able to find via the runner's own message id.

### Processing Chain

1. **`runNinaBackgroundTurn`** (`lib/nina/turnrun.ts`) builds `productionDeps(userId)`, overrides `toolSet: NINA_FULL_TOOL_SET` (send, lookup_runs, compare_runs, aggregate_runs, save_memory, generate_image, set_avatar), and calls into `lib/nina/turn.ts`.
2. **`runNinaTurnWith`/`runNinaTurn`** (`lib/nina/turn.ts`) calls `deps.client.messages.create(...)` (Anthropic Messages-shaped request against z.ai/GLM, `lib/llm/client.ts`) with `tools: toolSet.tools`. The model's `tool_use` blocks are parsed; up to `MAX_TOOL_ROUNDS = 2`; the loop ends on a `send` tool call, repaired once if malformed.
3. There is **no separate intent classifier**. "Intent" is entirely the model's tool choice, steered only by the system prompt (`lib/nina/prompts/system.ts`) and each tool's own `description` string in `lib/nina/prompts/tools.ts` — documented as measurably sensitive to wording (see that file's header comment, "one extra clause on one description took the same schema back down to 2/4 valid on the first attempt").
4. If the model calls `set_avatar` (`lib/nina/avatartools.ts:handleSetAvatar`): validates `{ scene, because }`, refuses if there is already an unannounced current avatar (`getCurrentNinaAvatar`), else calls `generateNinaAvatar({ userId, scene, source: 'generated' })` (`lib/nina/avatargen.ts`) — quota check, prompt build (`buildNinaImagePrompt`, `lib/nina/imagegen.ts`), opens a job row in `nina_turns` (`kind: 'image'`), fires generation (`lib/nina/imagerun.ts:fireNinaImageGeneration`). The model is told, in Indonesian, that the camera is running and **not** to claim the change already happened (`SET_AVATAR_ANSWERS.queued`).
5. If the model calls `generate_image` (`lib/nina/imagetools.ts:handleGenerateImage`): same generation machinery via `generateNinaSelfie` (`lib/nina/selfiegen.ts`), but the result is attached to a **chat bubble only** (`finishSelfie`, `lib/nina/imagerun.ts`) — it never touches `nina_avatars`.
6. **There is no third branch.** No tool call, at any point in this chain, can take an *existing* photo id and promote it to `nina_avatars` directly.

### The generation job's landing (async, both `set_avatar` and `generate_image`)

`lib/nina/imagerun.ts`:
- `finishSelfie` (~line 291) — writes `nina_messages` + `nina_message_images` (`kind: 'generated'`), captions it, pushes a `photo_delivered` push notification.
- `finishAvatar` (~line 527) — calls `insertNinaAvatarAsCurrent` (`lib/nina/queries/avatars.ts:120`): one `db.batch` that un-currents the old row and inserts the new one, `announced_at` left `NULL`. That `NULL` is exactly what `getUnannouncedCurrentNinaAvatar` (`lib/nina/queries/avatars.ts:91`) polls for; the proactive cron (`lib/nina/proactive.ts`, the `avatar_changed` trigger) makes her mention it on the next tick and then calls `markNinaAvatarAnnounced`.
- `closeFailed` (~line 560) — retry within budget, else a terminal failure + her apology (`NINA_IMAGE_APOLOGIES`).

### R1 — already fully implemented (no code needed)

- **Manual, mid-chat:** `set_avatar`'s own header states it is for *"he asks her to change it, or she decides to, mid-conversation"* — this is live today; `handleSetAvatar` has no gate on why she was asked.
- **Reward, tied to a run:** `lib/nina/promises.ts:161` calls `generateNinaAvatar({ userId, scene, source: 'generated' })` directly from the promise-fulfillment cron sweep (independent of whether the runner is currently chatting) — an `'avatar'`-kind promise (e.g. "I'll change my pic when you hit 10k") is honoured this way, and `promises.ts:310-320` even has a same-day "avatar landing" test for it.

Neither of these needs any change; they were misdiagnosed as broken only because R2 (below) does not exist and something has to stand in for it.

### R3 — already fully implemented (no code needed)

Case B ("ganti profpic lu pake FOTO BARU YANG MIRIP INI" — use a NEW photo similar to this one) is *exactly* `set_avatar`'s existing, correct behavior: a fresh generation, landed as her new avatar. The bug is not that this path is wrong — it is that it is the *only* path, so it fires even when the runner asked for R2 instead.

### R2 — the missing capability (what this plan adds)

No entry point, no tool, no handler. The nearest existing code is `lib/admin/ninaAlbumAvatarActions.ts:setChatPhotoAsAvatarAction` (admin-only, requires `requireAdmin()`, reachable only from `/admin/photos`'s framing panel) — proof that "copy an existing chat photo's bytes into a fresh `nina_avatars` row and make it current" is a solved, tested pattern; it simply has no chat-facing counterpart.

## Key Data Structures

### `NinaToolContext` (`lib/nina/tools.ts:177-188`)

```ts
export interface NinaToolContext {
  userId: string
  todayISO: DateISO
  history: NinaRunHistory
  gateway: NinaToolGateway
  sourceMessageId: string | null   // the runner message this turn answers; null on a proactive turn
}
```

No `sessionId`, no attached-image ids. A photo-adoption handler must derive both from `sourceMessageId` via a DB lookup — it cannot be handed them directly without a `NinaToolContext` change, which this plan avoids (see Impact Points).

### `NinaAvatarSource` (`lib/db/schema/nina/avatars.ts:16`)

```ts
export type NinaAvatarSource = 'seed' | 'generated' | 'operator' | 'admin'
```

`'generated'` — `set_avatar`/`generateNinaAvatar`/promise sweep. `'admin'` — `setChatPhotoAsAvatarAction`'s copy, and manual `/admin/nina` uploads. `'seed'` — the original bootstrap avatar. **`'operator'` has zero current writers or readers keying off it** — reserved, and the correct value for "a specific photo a person picked, via chat."

### `nina_message_images` (`lib/db/schema/nina/chat.ts:554`)

Key columns for this feature: `id`, `user_id`, `message_id` (nullable, `ON DELETE SET NULL`), `kind` (`'upload' | 'generated'`), `blob_url`, `pathname`, `width`/`height`/`bytes`, `description`, `source_avatar_id` / `source_image_id` (non-null ⇒ this row is a **re-share reference**, not an original — `isOriginalPhoto()` in `lib/nina/queries/images.ts:490` is the existing predicate that excludes these).

### `nina_avatars` (`lib/db/schema/nina/avatars.ts:214`)

Key columns: `id`, `user_id`, `blob_url`, `pathname`, `folder`, `filename`, `source_key` (unique per user — `nina_avatars_user_source_key_unq`), `source` (`NinaAvatarSource`), `is_current` (partial-unique per user), `announced_at` (`NULL` ⇒ not yet mentioned by her), `description`.

`source_key = 'chat-photo:<nina_message_images.id>'` is the existing convention (`setChatPhotoAsAvatarAction`) that makes re-adoption of the same photo idempotent — a second "use this photo" finds the first copy and just re-currents it instead of copying bytes twice.
