## Detailed Requirements Understanding

**Problem/Requirement Statement:** Nina currently has no way to answer a numeric-summary question ("what's my average pace this month", "how many kilometers did I run in August") without the caller first loading the *entire* reviewed run history into the turn and either doing the math in TypeScript herself (which no existing tool does — `lookup_runs` returns raw per-day facts, `compare_runs` returns a precomputed two-run diff) or having the model eyeball a list of rows and estimate. Neither path scales past a few months of data and neither guarantees numeric correctness. `AGGREGATE_RUNS_TOOL` closes this gap: given a metric, an aggregation function, a date range and an optional intent filter, it returns exactly one precomputed number (plus a count of runs it was computed over), sourced from a single SQL aggregate query.

**Success Criteria:**
- A new Anthropic tool (`aggregate_runs`) appears in `NINA_CORE_TOOL_SET` (or a set built from it) with a `Zod`-validated input schema, following the terse-description convention measured in `lib/nina/prompts/tools.ts`'s header.
- Its handler never loads per-run rows into the tool result — it returns a single aggregate value (and `n`, the count of runs contributing to it), computed by a genuine SQL `avg`/`sum`/`min`/`max`/`count` query.
- The new SQL query lives in `lib/db/queries/rollups.ts`, alongside `getAllTimeTotals` (the one existing SQL-aggregate example in this layer), userId-scoped and `reviewedAt IS NOT NULL`-gated like every other rollup.
- **Invariant 9 is preserved**: `lib/nina/tools.ts` (the dispatch file) and `lib/nina/prompts/tools.ts` (the schema file) do not import `runs`/the Drizzle schema or issue SQL directly. The new capability reaches the database only through `NinaToolGateway`, exactly like `loadRunHistory` does today.
- Existing tools, existing tests, and the tool-set layering (`NINA_CORE_TOOL_SET` → `NINA_CHAT_TOOL_SET` → `NINA_FULL_TOOL_SET`) are unaffected other than gaining the new tool.

**Key Considerations / Constraints:**
- z.ai's tool-choice here is `'any'` (force some tool), not per-tool-forced — Nina cannot be compelled to call `aggregate_runs` specifically, only nudged via the tool's `description` (the measured lever for this endpoint, see `prompts/tools.ts`'s header comment). This is a prompt-tuning concern, not a code contract, and is out of scope for this phase beyond writing a clear description.
- `additionalProperties: false` and terse, "REQUIRED."-prefixed property descriptions are the established convention; this is not decorative, it is measured to affect first-attempt-valid-call rates on this endpoint. The new schema must follow it.
- The five candidate metrics are only the ones already NOT NULL on every row (`durationSec`, `distanceM`, `avgPaceSec`) or commonly present (`avgHr`, `activeKcal`, `elevationM` are nullable) — `avg`/`sum` over a nullable column must use Postgres's null-skipping behavior (already relied on for `sum(...)` → `coalesce(..., 0)` in `getAllTimeTotals`); `min`/`max` naturally skip nulls; `count` should count non-null values of the chosen metric, not just matching rows, so a question like "how many runs have a recorded elevation gain" is answerable too — this is a design choice for the phase to state explicitly (see Decisions below).
- Date range: the model computes `from`/`to` as ISO dates itself from `NinaContext.now.todayISO` (the same convention `lookup_runs`/`compare_runs` use — RU-13, no server-side natural-language date parsing). The query is a half-open range scan (`>= from AND < toExclusive`) to use `runs_user_occurred_idx`, matching every other rollup in the file — this means the tool's public contract should accept an **inclusive** end date (what a model naturally reasons in — "the last 2 months" ends today, inclusive) and the handler converts to the exclusive bound internally, the same translation `monthRange`/`isoWeekRange` already do for their callers.
- `reviewedAt IS NOT NULL` gate is non-negotiable (D16, applied by every existing rollup and by `getReviewedRunsWithChildren`) — an unreviewed extraction is a number nobody vouched for.
- Single-user app (`plan invariant 7`, restated in `lib/db/schema.ts:487`) — no multi-tenant concerns beyond the existing `userId` scoping convention, which must still be followed literally (every rollup takes `userId` first and puts it in the `WHERE`).
- No sandbox, no dynamic SQL, no free-form code execution anywhere in this repo (confirmed absent: no `eval(`, `vm.`, `isolated-vm`, `pyodide`) — this phase must not introduce one. The tool's `metric`/`agg` fields are closed enums, not strings interpolated into SQL.

**Assumptions:**
- "avg/sum/min/max/count" is the complete list of aggregations wanted for v1 (no percentiles, no group-by-week/month bucketing) — matches the user's literal ask.
- The six metrics named by the user (`durationSec`, `distanceM`, `avgPaceSec`, `avgHr`, `activeKcal`, `elevationM`) are the complete metric list for v1; anything else (`avgCadence`, `maxHr`, etc.) is a future addition, not in scope.
- `intent` is the only optional filter for v1 (matches the user's ask); no filter by `source` (screenshot/manual) or by weekday.
- The new tool is added to `NINA_CORE_TOOL_SET` directly in `lib/nina/tools.ts` (not via a separate `extendToolSet` file), because it is a pure DB-read capability with the exact same shape and dependency profile as `lookup_runs`/`compare_runs`, which already live there — the `extendToolSet` convention in `imagetools.ts`/`avatartools.ts` exists specifically to keep image-generation's separate infrastructure (OpenRouter, job rows, avatar rotation) out of this file, a concern that does not apply here. This reading is a departure from the user's literal phrasing ("handler wired via extendToolSet() in lib/nina/tools.ts") — see Decisions.

## Current Dataflow

### Entry Point: a chat turn that asks a numeric-summary question

**Location:** `lib/nina/turn.ts` (`runNinaTurn`/`runNinaTurnWith`), reached from `lib/nina/turnrun.ts`'s chat-turn action.
**Trigger:** the runner sends a chat message; the turn loop calls z.ai's Anthropic-compatible endpoint with `tools: deps.toolSet.tools` and `tool_choice: 'any'`.
**Input Schema:** whatever `NinaToolSet.tools` currently is (`NINA_FULL_TOOL_SET` in production) — an `Anthropic.Tool[]`.
**Next step today:** if the model wants run data, it can only call `lookup_runs` (specific days) or `compare_runs` (two days, precomputed diff). There is no path to a range-aggregate; a question like "average duration over 2 months" today either goes unanswered by any tool (the model tries to answer directly, ungrounded) or the model calls `lookup_runs` with a burst of individual dates (capped at `maxItems: 5`, per `LOOKUP_RUNS_TOOL`), gets raw per-day facts, and has to average them itself in prose — inaccurate and expensive past 5 days.

### Processing Chain (existing `lookup_runs`, for contrast)

1. **Function:** `handleLookupRuns()` — `lib/nina/tools.ts:398`
   - **Input:** `{ dates: string[] }`, Zod-validated by `LookupRunsArgsSchema`.
   - **Transform:** resolves each date against `ctx.history.index` (the FULL in-memory run history, already loaded once per turn by `NinaToolGateway.loadRunHistory`) — no new DB read per call.
   - **Output:** one `LookupDay` per requested date, each carrying full per-run facts (splits, zones, HR).
   - **Calls:** nothing further; returns straight to `dispatchNinaTool`.

2. **Function:** `loadRunHistory()` — `lib/nina/gateway.ts:347`
   - **Input:** `userId`.
   - **Transform:** `Promise.all([getReviewedRunsWithChildren(userId), resolveHrMax(userId)])`, then maps every row through `toDetailedRun`.
   - **Output:** `NinaRunHistory` (all reviewed runs, indexed by date) — built once per turn, before the first model call (`NinaToolContext.history`).
   - **Calls:** `lib/db/queries/rollups.ts:getReviewedRunsWithChildren` — three statements, one `db.batch`, the whole reviewed history.

### Data Persistence

**Database:** Neon Postgres via `drizzle-orm/neon-http` (`lib/db/index.ts`), no `db.transaction()` support (`db.batch` used instead). `runs` table: `lib/db/schema/runs.ts:182`, indexed on `(userId, occurredOn DESC)` (`runs_user_occurred_idx`) and `(userId, maxHr DESC)`.
**No cache** in this path — every turn re-loads the full history (module header in `lib/nina/tools.ts:71-75` explicitly accepts this at "~200 runs a year, one user" scale).

### Exit Points
- `NinaToolAnswer.answer` is JSON-serialized straight into an Anthropic `tool_result` content block (`lib/nina/tools.ts:141`), read by the model on its next round.
- The turn ends when the model calls `send` (`SEND_TOOL`), producing the chat bubbles the runner sees.

### Function: `getAllTimeTotals` (the pattern to follow)
**Location:** `lib/db/queries/rollups.ts:163-175`
```ts
const rows = await db
  .select({
    runCount: sql<number>`count(*)`.mapWith(Number),
    distanceM: sql<number>`coalesce(sum(${runs.distanceM}), 0)`.mapWith(Number),
    durationSec: sql<number>`coalesce(sum(${runs.durationSec}), 0)`.mapWith(Number),
    firstRunOn: sql<string | null>`min(${runs.occurredOn})`,
    lastRunOn: sql<string | null>`max(${runs.occurredOn})`,
  })
  .from(runs)
  .where(and(eq(runs.userId, userId), isNotNull(runs.reviewedAt)))
```
This is the only existing SQL-aggregate query in the codebase and the direct template for the new function — a `db.select({ ... sql`...` ... }).from(runs).where(...)` with no row materialization, generalized to a chosen metric column, a chosen aggregate function, a date range, and an optional intent filter.
